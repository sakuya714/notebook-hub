## EAの参照モデル（★） {{learning/応用情報技術者:06-1#EA}}
==EA は会社の業務とシステムを4層の設計図で整理する。参照モデルは各層の「お手本の分類表」==。
@stack EA の4つの体系（上ほど業務、下ほど技術）
ビジネス（BA） :: 業務の流れ。**BRM**（業務の分類）と **PRM**（成果の測り方＝KPI）
データ（DA） :: どんなデータを持つか。**DRM**（データの名称・定義・属性）
+アプリケーション（AA） :: 業務を動かすシステム。**SRM**（機能を**部品化**して再利用）
+テクノロジ（TA） :: それを支える技術基盤。**TRM**（**技術の標準化**）
@end
> 家を建てるなら：何を建て（B）どう評価するか（P）→ 材料（D）→ 部品（S）→ 土台（T）
| 問題文の言葉 | モデル |
| 業績・成果・**KPI** | PRM（Performance） |
| 業務の**分類・体系** | BRM（Business） |
| データの**名称・定義・属性** | DRM（Data） |
+| 機能の**部品化・再利用** | SRM（Service component） |
+| **技術の標準化**・プラットフォーム | TRM（Technical） |
! SRM は**部品そのもの**、TRM は部品が乗る**土台**。「再利用・コンポーネント」→ SRM、「標準化・基盤」→ TRM
- As-Is と To-Be — **現状**モデル → **理想**モデル → 間を埋める**移行計画**の順に作る
@pair EA | SRM | TRM | 機能の部品化・再利用 ／ 技術の標準化・基盤 | T1

## SOAとマッシュアップ {{learning/応用情報技術者:06-1#借りる}}
==SOA は自社の業務機能を「サービス」という部品にして、組み合わせてシステムを作る==。
| 名前 | 一言で | 例 |
+| SOA | 業務機能を**サービス（部品）**にして組み合わせる | 受注・在庫・請求のサービスをつないで販売システム |

## 分析の枠組み {{learning/応用情報技術者:06-1#競争を分析する}}
@mx アンゾフの成長マトリクス（製品×市場）
x: 今の製品 | 新しい製品
y: 今の市場 | 新しい市場
TL: +市場浸透 :: 今の客に今の商品を**もっと売る**（ハンバーガー店のクーポン）
TR: 製品開発 :: 今の客に**新商品**（新しいバーガー）
BL: +市場開拓 :: 今の商品を**新しい客・地域**へ（海外に出店）
BR: 多角化 :: 新しい客に新しい商品。**一番リスクが高い**（ホテル業を始める）
@end
> **浸透**＝今の市場に**しみ込ませる**、**開拓**＝新しい市場を**切り開く**。製品が新しければ**開発**、両方新しければ**多角化**
| 枠組み | 何を見る？ |
| SWOT | 内部の**強み・弱み** × 外部の**機会・脅威** |
| PPM | **市場成長率 × 占有率**で事業を4つに（花形・金のなる木・問題児・負け犬） |
| BSC | **財務・顧客・業務プロセス・学習と成長**の4つの視点で目標を立てる |
| PLC | 製品の一生：導入 → 成長 → 成熟 → 衰退 |
@pair 2×2 | アンゾフ | PPM | 製品×市場で伸ばす方向 ／ 成長率×占有率でお金の配分 | T1

## IoTとCPS {{learning/応用情報技術者:06-1#IoT}}
==デジタルツインは現実の「双子」を仮想空間に作って試す。CPS は現実 → 仮想 → 現実と回す仕組み全体==。
| 言葉 | 一言で |
+| デジタルツイン | 現実の物を**仮想空間にそっくり再現**し、試してから現実に反映 |
| CPS | 現実のデータを集め → 仮想で分析 → **現実に返す**仕組み全体 |
| エッジコンピューティング | クラウドまで送らず**現場の近く**で処理（速い・通信が減る） |
| スマートグリッド | 電力網を IT で**賢く制御**（需要と供給を合わせる） |
| スマートメーター | 通信機能つきの**電力量計**（検針に行かなくていい） |
> twin＝**双子**。双子の方で試してから本物を動かす（工場ラインの変更を仮想空間で先に試す）
( IoT の電気
+ エネルギーハーベスティング — 光・振動・熱など**周りの小さなエネルギーを集めて**電気にする（電池交換いらず）
- ノーマリーオフ — 使わない部分の電源を**こまめに切る**（不揮発メモリで状態を保つ）
- PoE — **LAN ケーブルで電気も送る**（監視カメラ・無線 LAN の親機）
- EMS — エネルギーの使い方を**管理**して省エネ（HEMS＝家、BEMS＝ビル、FEMS＝工場）
)
! EMS は2つある：エネルギー管理（Energy Management System）／電子機器の受託製造（Electronics Manufacturing Service）
@pair IoT | デジタルツイン | CPS | 仮想空間の双子で試す ／ 現実→仮想→現実を回す仕組み全体 | T1

@ch T2 | 売り方 | 市場を分ける → 好みを測る → 売り込み方 → 集めて見せる

## 知的財産権（★） {{learning/応用情報技術者:06-3#知的財産権}}
==「4つ」は産業財産権だけの話。著作権・営業秘密などもある==。登録が要るのは産業財産権の4つだけ。
@fig ipr | 知的財産権の地図 | オレンジ＝特許庁に出願・登録が要る4つ（産業財産権）

| 権利 | 守るもの | 期間 |
+| 特許権 | 技術的な**アイデア（発明）** | **出願から20年** |
| 実用新案権 | 物の**形・構造**の工夫 | 出願から10年 |
| 意匠権 | 見た目の**デザイン** | 出願から25年 |
| 商標権 | 商品の**名前・ロゴ** | 登録から10年（**更新できる**） |
+| 著作権 | **表現**（文章・音楽・プログラム） | 死後70年（**登録いらず**） |

- 営業秘密（不正競争防止法） — **秘密として管理**・**役に立つ**・**知られていない**の3つがそろった情報（顧客名簿・製法）
- 回路配置利用権 — 半導体チップの**回路の配置**
- 育成者権 — 植物の**新品種**
)

## 著作権は誰のもの {{learning/応用情報技術者:06-3#知的財産権}}
==原則は作った人。ただし会社の仕事として作ったら会社==（職務著作）。契約で別に決めていない場合の話。
| 作り方 | 誰のもの？ | 理由 |
| 社員が仕事で | **会社** | 職務著作 |
+| 請負で外注 | **作った受注側** | 代金を払っても権利は**自動では移らない** |
+| 派遣社員が | **派遣先**（働いた会社） | 派遣先の指示で、その会社の仕事として作ったから |
> 家を建ててもらうのとは違う。プログラムの著作権が欲しければ、契約書に「**譲渡する**」と書く
! 「請負で発注者のもの」「派遣元のもの」は×（契約で決めていなければ）

## 請負と準委任 {{learning/応用情報技術者:06-3#働かせ方と頼み方}}
==請負は「完成させる」約束、準委任は「きちんと作業する」約束==。
| 契約 | 約束するもの | 指示を出すのは |
+| 請負 | **完成**（成果物）。不具合は直す責任（契約不適合責任） | 受注側（発注者は**直接指示できない**） |
| 準委任 | **きちんと作業する**こと（完成の義務はない） | 受注側 |
| 派遣 | **人を貸す** | **派遣先**が直接指示する |
> 請負＝**大工**に家を建ててもらう（完成させる約束）、準委任＝**家庭教師**（合格の保証はないが、ちゃんと教える約束）
! 請負なのに発注者が受注側の人へ**直接指示**すると**偽装請負**。指示したいなら派遣契約にする
( 工程ごとの向き
- 要件定義 — **準委任**（何を作るかまだ決まっていない）
- 外部設計 — どちらも（要件が固まっていれば請負）
+ 内部設計〜結合テスト — **請負**（作る物がはっきりしている）
- システムテスト — どちらも
- 導入・運用 — **準委任**（ずっと続く作業）
)
- 下請法 — 発注側が立場を利用して**支払いを遅らせる・買いたたく**のを禁じる。2026年1月から**取適法**（中小受託取引適正化法）に名前が変わった
@pair 契約 | 請負 | 準委任 | 完成させる約束 ／ きちんと作業する約束 | T4

## 調達の流れ {{learning/応用情報技術者:06-3#働かせ方と頼み方}}
@fig procure | 調達の流れ | RFI・RFP は契約の前、RFC は契約の後
| 言葉 | 一言で |
| RFI（Information） | どんな技術・製品・実績があるか**情報をください** |
+| RFP（Proposal） | この要件で**提案書と見積りをください** |
| RFC（Change） | 契約した後の**変更依頼** |
> 宴会の予約で：RFI＝「どんなコースがありますか？」、RFP＝「10人・予算5万円でコースを提案して」、RFC＝「1人増えたので変えて」
! RFC は2つある：変更依頼（Request for **Change**）／インターネット技術の標準文書（Request for **Comments**。TCP/IP の仕様書など）
@pair 調達 | RFI | RFP | 情報をください ／ 提案書と見積りをください | T4

## RoHSと仲間 {{learning/応用情報技術者:06-3#守るルール}}
==RoHS は電気・電子機器に有害物質を使わせない EU のルール==（鉛・水銀・カドミウムなど**10物質**）。
| ルール | 一言で |
+| RoHS 指令 | 電気・電子機器の**有害物質の使用を制限** |
| WEEE 指令 | 使い終わった電気・電子機器の**回収・リサイクル** |
| EMC 指令 | 電磁波で**ほかの機器を邪魔しない・邪魔されない** |
| 外為法 | 武器に使える技術・製品の**輸出を規制**（安全保障貿易管理） |
> RoHS＝**R**estriction **o**f **H**azardous **S**ubstances（有害物質の制限）。作るときの話が RoHS、捨てるときの話が WEEE

## トレーサビリティ {{learning/応用情報技術者:06-3#共通のルール}}
==「なぜ今こうなっているか」を、記録をたどって**さかのぼれる**こと==（trace＝たどる）。
+ 開発では — 要求 ⇄ 設計 ⇄ プログラム ⇄ テストの対応と**変更の経緯**が残っていて、**どちら向きにもたどれる**。要求が変わったら直す所がすぐわかる
- 食品では — パックの番号から**どの農家のどの牛か**までたどれる
> Git のコミット履歴に「何を・なぜ変えたか」が残っていて、過去の判断までさかのぼれる状態
! 「仕様を固めたら以降は変更できない」はトレーサビリティではない。変更が起きても**元の要求までさかのぼって確かめられる**こと
