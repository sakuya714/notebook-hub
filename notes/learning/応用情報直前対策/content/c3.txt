## 3層スキーマ {{learning/応用情報技術者:03-1#3層スキーマ}}
==外部＝見せ方、概念＝中身、内部＝しまい方==。1つの層を変えても、ほかの層に響かないように分ける（**データの独立性**）。
| 層 | 一言で | 具体的な作業 |
| 外部 | 使う人ごとの**見え方** | **ビュー** |
+| 概念 | **データの中身と関係** | **E-R図**・表の定義・**正規化**・**一意性制約・参照制約** |
+| 内部 | **ディスクへのしまい方** | **インデックス**・ファイル編成 |
> 図書館で例えると：外部＝利用者用と司書用の**検索画面**、概念＝本・著者・利用者が**何の項目を持ち、どうつながるか**、内部＝本を**どの棚にどう並べるか**・索引カードを作るか
! 制約（一意性・参照）は「データとして正しいか」のルールなので**概念**。インデックスは「**速く探すためのしまい方**」なので**内部**
| 担当 | 受け持つ所 |
+| DA（データ管理者） | **概念**：論理設計・データ項目の**標準化** |
| DBA（データベース管理者） | **内部と運用**：性能チューニング・容量計画・障害復旧 |
@pair 担当 | DA | DBA | データの中身（論理設計・項目の標準化）／ DBという機械（性能・容量・障害） | D1

## キーの入れ子 {{learning/応用情報技術者:03-1#キーの種類}}
@lad キーの入れ子（例：社員表＝社員番号・免許証番号・氏名） | 広い | 狭い
スーパーキー :: 1行を特定**できれば**何でも。余計な列が入っていてもいい。例 {社員番号, 氏名}
+候補キー :: 余計な列を削りきった**極小**の組。例 {社員番号}・{免許証番号}
主キー :: 候補キーから**1つ選んだ代表**。重複不可・NULL不可
@end
> 日本 ⊃ 大阪 ⊃ 梅田と同じ。**スーパーキー ⊃ 候補キー ⊃ 主キー**。外部キーだけは別枠
( 入れ子の外の2つ
+ 代替キー — 主キーに**選ばれなかった**候補キー（免許証番号）
+ 外部キー — **ほかの表の主キーを参照する**列。行を特定するためではなく、**表どうしをつなぐ**ため
- 代理キー（サロゲートキー） — 意味のない**連番**を主キーにしたもの。代替キーとは別物
)
| 問題文の言葉 | 答え |
+| **参照する** | 外部キー |
| **極小** | 候補キー |
| 〜を含む集合（極小でない） | スーパーキー |
| 主キー**以外で**一意に識別 | 代替キー |

## 参照制約の削除ルール {{learning/応用情報技術者:03-1#制約と表定義}}
親（注文）を消したとき、それを参照している子（注文明細）をどうするかのルール。
| ルール | 親を消したら子は？ |
+| CASCADE | **子も一緒に消える**（連鎖） |
| RESTRICT | 子がいたら親を**消させない**（すぐ拒否） |
| NO ACTION | 子がいたら消させない（最後に確かめる。ふつうの既定値） |
| SET NULL | 子の外部キーを **NULL** にする |
| SET DEFAULT | 子の外部キーを**初期値**にする |
> CASCADE＝**滝**。上が崩れたら下も流れ落ちる
- UNIQUE — 値の**重複禁止**（削除ルールではない）
- INTERSECT — 2つの表の**共通部分**を取る SQL

## 更新できるビュー {{learning/応用情報技術者:03-1#更新とビュー}}
==ビューの1行が、元の表のどの1行かはっきりわかれば更新できる==。WHERE で絞るだけなら OK。
+ 更新できない — **まとめる操作**が入ったとき：集約関数（AVG・SUM・COUNT…）・GROUP BY・DISTINCT・複数の表の結合
> 「クラスの平均点」を70から75に書き換えても、**誰の点を変えればいいか**わからない
+ ストアドプロシージャ — 処理を DB 側にまとめて置き、1回の呼び出しで実行する。減るのは**アプリと DB の間の通信**だけ
> 出前を1品ずつ電話する代わりに「**いつものセット**」で1回だけ電話する。厨房で作る料理（DB の中の処理）の数は同じ
! 「DBMS の中の実行計画・バッファ・ディスク I/O が減る」は全部×。減るのは**ネットワーク（通信）**の方

@ch D2 | 壊さない・ためて使う | トランザクション → 障害回復 → 2相コミット → CAP → DWH
@map
flow: ACID::1件の処理を壊さない > undo・redo::障害から戻す > 2相コミット::複数のDBで全部か無か > +CAP::分散したら2つまで > DWH::ためて分析
同じ「一貫性」が ACID と CAP で別の意味になるのが一番のひっかけ。
@end

## 一貫性が2つある（★） {{learning/応用情報技術者:03-2#トランザクション}}
==ACID の C は「決まりを破らない」、CAP の C は「複製どうしが同じ値」==。同じ言葉で中身が違う。
| | ACID の C | CAP の C |
+| 意味 | **決まり（制約）を破らない**（残高がマイナスにならない） | **複製どうしが同じ値**（どこで見ても同じ） |
| 何の話 | 1件のトランザクション | 分散したデータベース |
( ACID（トランザクションの4つの性質）
- A 原子性 — **全部やるか、全部やらないか**
- C 一貫性 — 決まりを破らない
- I 独立性 — 同時に動いても**互いに影響しない**
- D 耐久性 — 確定したら**障害でも消えない**
)
( CAP 定理（分散したら3つのうち2つまで）
+ C 一貫性 — どこで見ても同じデータ
+ A 可用性 — いつでも使える
+ P 分断耐性 — ネットワークが途中で切れても動き続ける
)
> 本店と支店で在庫を共有していて、間の回線が切れたら：在庫をそろえるため**販売を止める**（C を守って A を捨てる）か、各店で売り続けて**在庫がずれる**（A を守って C を捨てる）か
| 組合せ | 捨てるもの | 例 |
| CA | 分散しない（P） | 1台の RDB |
+| CP | 止まることがある（A） | 銀行 |
+| AP | 一時的にずれる（C） | SNS のいいね数 |
- BASE — AP 寄りの考え方。「**最終的に**そろえばいい」（結果整合性）
@pair 一貫性 | ACIDのC | CAPのC | 決まり（制約）を破らない ／ 複製どうしが同じ値 | D2

## 障害回復（undo と redo） {{learning/応用情報技術者:03-2#障害回復}}
| 処理 | 何をする？ | 使うログ ／ 対象 |
+| undo | **取り消して元に戻す**（ロールバック） | **更新前** ／ **未コミット** |
+| redo | **もう一回やり直す**（ロールフォワード） | **更新後** ／ **コミット済み** |
> Word と同じ：**元に戻す**には変更**前**の文、**やり直す**には変更**後**の文が要る
| 障害が起きたときの状態 | 処理 |
| チェックポイント**前**に完了 | 何もしない（書き込み済み） |
+| チェックポイント**後**にコミット | **redo** |
+| 障害の時点で**途中**（未コミット） | **undo** |
- チェックポイント — メモリの内容を**ディスクに書き出した時点**。復旧はそこから後だけ見ればいい
- ロールバック — 障害のときだけでなく、ふだんの「やっぱりやめた」（SQL の ROLLBACK）にも使う言葉
@pair 障害回復 | ロールバック（undo） | ロールフォワード（redo） | 更新前ログで取り消す（未コミット）／ 更新後ログでやり直す（コミット済み） | D2

## 2相コミット {{learning/応用情報技術者:03-2#分散DB}}
複数の DB で「**全部成功か、全部取り消しか**」を守る。第1相「コミットしていい？」→「OK、待ってます」、第2相「じゃあコミット（取り消し）して」。
+* 詰むのは1か所だけ — 参加者が「**OK（待機）と答えた後、決定が届く前**」に調停者が消えたとき。約束したので勝手に決められない（**ブロッキング**）
- それ以外の障害 — 答える前ならタイムアウトで取り消し、決定を受け取った後なら復旧してやり直すだけ
> 飲み会の幹事：「金曜行ける？」→ みんな「行ける、空けとく」→ 幹事が**決定か中止を言う前に音信不通**。誰もほかの予定を入れられない

## ためる場所と使い方（★） {{learning/応用情報技術者:03-2#DWHと分析}}
==生のまま放り込むのがデータレイク、整理して時系列でためるのが DWH、部門用に切り出すのがデータマート==。
@stack ためる場所（上ほど生、下ほど用途向け）
データレイク :: **生データをそのまま**何でも放り込む（形式バラバラでいい）。何でも入る大きな冷凍庫
+データウェアハウス（DWH） :: 分析用に**整理・統合**して**時系列**でためる。下ごしらえ済みの倉庫
データマート :: DWH から**部門・用途ごとに切り出した**小さい版。和食部門の冷蔵庫
@end
! クラスタシステム（複数のサーバに複製して性能・可用性を上げる）は、ためる場所でも分析でもない。選択肢のダミーとして混ざる
| 使い方 | 一言で |
| ETL | 元のデータを**抽出・変換・格納**して DWH に入れる |
+| データマイニング | 大量のデータから**隠れた規則・相関**を見つける（ビールとおむつ） |
| OLAP | **いろいろな切り口で集計**（ドリルダウン・スライス） |
| BI ツール | グラフ・ダッシュボードで**見える化** |
( スタースキーマ（真ん中にレシート、周りに名簿）
+ ファクトテーブル — 真ん中。**起きた出来事と数字**（売上・数量）＝レシートの束。どんどん増える
+ ディメンションテーブル — 周り。**分析の切り口**（顧客・商品・店舗・日付）＝名簿・カタログ
- サマリテーブル — 集計した**結果**をあらかじめ保存した表
- ルックアップテーブル — 決まった**値の一覧**（コード表）
)
> **Fact＝事実**（起きた売上）、**Dimension＝次元**（どの角度から見るか）
@pair DWH | ファクトテーブル | ディメンションテーブル | 分析の対象（出来事と数値）／ 分析の切り口（顧客・商品） | D2
@pair DWH | データレイク | データマート | 生のまま何でもためる ／ DWHから部門用に切り出す | D2
