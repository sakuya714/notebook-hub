## UMLの図 {{learning/応用情報技術者:04-1#UML}}
==構造図は「何でできているか」、振る舞い図は「どう動くか」==。全14種類、出るのはほぼ下の7つ。
| 判定の言葉 | 図 | ネットショップで |
+| **アクター**・利用者の視点 | ユースケース図 | 客は「探す・買う」、店長は「商品を登録」 |
+| **時系列**・メッセージの順序 | シーケンス図 | 客 → 画面 → 注文処理 → 在庫DB の順に呼ぶ |
| **状態**・遷移・イベント | ステートマシン図 | 注文：受付 → 支払済 → 発送 → 配達完了 |
| **処理の流れ**・分岐・並行 | アクティビティ図 | カート → 支払い → 在庫あり？ → 発送 |
| 属性・操作・**多重度** | クラス図 | 会員・商品・注文の項目とつながり |
| ソフトの**部品** | コンポーネント図 | 決済部品・在庫部品 |
| **ノード**・物理的な配置 | 配置図 | Webサーバ・DBサーバに何を置くか |
( 似ているペア
- シーケンス図 ／ コミュニケーション図 — 同じやりとりを**時間順**で描く ／ **つながり**で描く
- アクティビティ図 ／ ステートマシン図 — **処理の流れ** ／ **1つの物の状態**の変化
- クラス図 ／ オブジェクト図 — **設計図（型）** ／ ある瞬間の**具体的なデータ**
- コンポーネント図 ／ 配置図 — **ソフトの部品** ／ **マシンへの配置**
)
@pair UML | シーケンス図 | コミュニケーション図 | 時間の順に描く ／ つながりで描く | M1
@pair UML | アクティビティ図 | ステートマシン図 | 処理の流れ ／ 1つの物の状態の変化 | M1

## 結合度と強度 {{learning/応用情報技術者:04-1#結合度と強度}}
==結合度（モジュールどうし）は弱いほど良い、強度（モジュールの中）は強いほど良い==。合言葉は**疎結合・高凝集**。
@lad 結合度（良い順）＝「です、背が今日ない」 | 弱い＝良い | 強い＝悪い
データ結合 :: 引数で**単一のデータ**
スタンプ結合 :: 引数で**構造体**
制御結合 :: 引数で**動作を指示**（フラグ）
外部結合 :: **グローバル変数**（単一）
+共通結合 :: **グローバルな構造体**
内容結合 :: 相手の**内部を直接**いじる（JUMP）
@end
+ 結合度の判定 — 「**引数**」→ データ・スタンプ・制御（中身が単一？構造体？指示？）、「**大域・グローバル**」→ 外部（単一）・共通（構造体）、「**内部を直接・JUMP**」→ 内容
> 結合度はどちらのグループも「**単一より構造体の方が強い（悪い）**」
@lad 強度（良い順）＝「気丈に連れて、持論案」 | 強い＝良い | 弱い＝悪い
+機能的強度 :: **1つの機能**だけ
情報的強度 :: **同じデータ**を扱う機能を集めた（入口は別々）
連絡的強度 :: 同じデータを使って**順番に**処理
手順的強度 :: 決まった**手順の順**に並べた
時間的強度 :: **同じタイミング**で動く（初期化処理）
論理的強度 :: **似た処理**をまとめてフラグで切り替え
暗合的強度 :: **たまたま**寄せ集めただけ
@end
> 強度は「**まとめた理由**がちゃんとしているほど良い」。機能（1つの目的）が最強、たまたま（暗合）が最弱
@pair 結合度 | 外部結合 | 共通結合 | 大域の単一データ ／ 大域の構造体 | M1

## 網羅（★） {{learning/応用情報技術者:04-1#テスト}}
==分岐網羅は if の「結果」を、条件網羅は if の中の「部品」を、両方の値で試す==。
| A | B | A and B |
| 真 | 真 | **Yes** |
| 真 | 偽 | No |
| 偽 | 真 | No |
| 偽 | 偽 | No |

| 網羅 | 何を両方出す？ | 合格の例 |
| 命令網羅（C0） | **全部の命令**を1回は通す | 真真（命令を通るケース1つ） |
+| 分岐網羅（C1） | 判定の**結果**の Yes・No | 真真 ＋ 偽偽 |
+| 条件網羅 | **A・B それぞれ**の真・偽 | 真偽 ＋ 偽真（でも結果は両方 No） |
| 判定条件／条件網羅 | 上の2つを**両方** | 真真 ＋ 偽偽 |
| 複数条件網羅 | A・B の**組合せ全部** | 4通り全部 |
+* 分岐網羅 ＝ 判定条件網羅 — 名前が2つあるだけで**同じもの**。「／条件」が付いた判定条件／条件網羅は別物
+ 条件網羅の弱点 — 真偽＋偽真なら A も B も真偽を両方試したのに、結果は**一度も Yes にならない** → 条件網羅を満たしても分岐網羅を満たすとは限らない
> テストで例えると：分岐網羅＝**合格・不合格の両方**を試す、条件網羅＝**国語と数学それぞれ**の良い・悪いを試す（全体で合格するケースが抜けるかも）
@lad 網羅の強さ | 弱い | 強い
命令網羅（C0） :: 全部の命令を通す
+分岐網羅（C1） :: 判定の Yes・No を両方
判定条件／条件網羅 :: 分岐＋条件の両方
複数条件網羅 :: 組合せを全部
@end
+ 最少のテストケースの探し方 — ひし形ごとに Yes と No を1回ずつ通すまで、**上から順に変数の値を追う**。前のひし形の処理で値が変わる（C ← A×C など）ので、次のひし形は**変わった後の値**で判定する
! 条件網羅は分岐網羅との強さの順に入らない（別枠）。「網羅率」の計算では、命令は**全命令のうち通った数**、分岐は**全分岐先のうち通った数**（10個中8個 → 80%）
@pair 網羅 | 分岐網羅 | 条件網羅 | 判定の結果の真偽 ／ 個々の条件の真偽 | M1

## 故障の分析（FTA） {{learning/応用情報技術者:04-1#故障と不具合の分析}}
==FTA は悪い結果を一番上に置き、原因を木の形で上から下へ分解する==（Fault Tree＝故障の木）。
| 手法 | 向き | 一言で |
+| FTA | **トップダウン**（結果 → 原因） | 「止まった。なんで？」を AND・OR ゲートの**樹形図**で |
| FMEA | **ボトムアップ**（原因 → 結果） | 部品ごとに「**これが壊れたらどうなる？**」 |
| ODC分析 | — | バグを決まった**分類に仕分け**て、どこに集中しているか |
| RCA | — | **なぜなぜ分析**で根本原因を探す |
- AND ゲート ／ OR ゲート — 下が**全部**そろったら上が起きる ／ 下の**どれか1つ**で上が起きる（論理回路と同じ記号）
@pair 故障の分析 | FTA | FMEA | 結果から原因へ（トップダウン）／ 部品の故障から影響へ（ボトムアップ） | M1

## KPT {{learning/応用情報技術者:04-2#アジャイル}}
スクラムのふりかえり（レトロスペクティブ）でよく使う3つの箱。
| KPT | 意味 | 語尾 |
| Keep | 良かった、**続けること** | 「〜を続ける」 |
| Problem | **起きた問題** | 「〜だった」「〜かかった」（過去） |

## 保守の4種類（★） {{learning/応用情報技術者:04-2#再利用と保守}}
==2つの質問で決まる。「バグの話？」→「もう起きた？」または「外が変わった？」==。
@fig hoshu | 保守の4種類（JIS X 0161） | 適応保守は必ず「外の何か（OS・法律・機器）が変わった」が理由。それがなければ完全化

## リスクアセスメント（★） {{learning/応用情報技術者:05-1#品質とリスク}}
==特定（見つける）→ 分析（測る）→ 評価（決める）までがリスクアセスメント==。対応（やる）は入らない（JIS Q 31000）。
@fig riskflow | リスクマネジメントの4段階 | アセスメント＝Assessment（査定）。調べて判断するところまで
| 段階 | 問題文にこの言葉 |
+| 特定 | **資産・資源の性質と価値**、リスク源・脅威・脆弱性を**洗い出す** |
+| 分析 | **起こりやすさ**、結果の**性質と大きさ** |
| 評価 | リスク基準と**比べる**、**優先順位** |
| 対応 | **残留リスク**、回避・低減・移転・保有 |
> 家の防災で：何がある？何が起こる？（特定）→ 地震は起きやすい？被害は？（分析）→ 地震対策を最優先に（評価）→ 保険・耐震補強（対応）
! 「大きさ」「起こりやすさ」が出たら全部**分析**（2回とも分析の選択肢に引っかかった）。選択肢に「リスク対応」が入っていたらアセスメントではない
@pair リスク | リスク分析 | リスク評価 | 起こりやすさ・大きさを測る ／ 基準と比べて優先順位を決める | M2

## BIAとBCP {{learning/応用情報技術者:05-2#事業継続}}
==BIA で「止まったらどれだけ困るか」を調べ、目標を決め、BCP で「止まったらこう動く」を決める==。
| 目標 | 意味 | ラーメン屋が火事になったら |
+| RPO（Point） | **いつの時点**のデータまで戻すか | 昨日の閉店時点の売上データまで |
+| RTO（Time） | **何時間で**再開するか | 3日以内に営業再開 |
| RLO（Level） | **どの水準**まで戻すか | まずはラーメン1種類だけで |
> 最後の英単語を見るだけ：**P**oint＝時点、**T**ime＝時間、**L**evel＝水準
+ 業務再開フェーズ — **代替手段**（バックアップサイト・手作業）で最低限を再開（キッチンカーで営業）。回復で範囲を広げ、全面復旧で通常運用に戻す
@fig bcpflow | BCP の4つのフェーズ | 発動 → 再開 → 回復 → 全面復旧
@pair BCP | RPO | RTO | どの時点まで戻すか ／ 何時間で再開するか | M2

## 監査人は促すまで {{learning/応用情報技術者:05-2#内部統制}}
==調べる・報告する・改善を勧めるまでがOK、自分で直すのはNG==。直すのは経営者・監査を受けた部門。自分で直すと、次の監査で自分の宿題を自分で採点することになる（**独立性**がなくなる）。
| 人 | 役割 |
| 経営者 | 内部統制を**整備・運用**する**最終責任者** |
| 取締役会 | 内部統制の**基本方針を決める** |
| 監査役 | 取締役の仕事を**独立した立場で監視** |
+| 内部監査人 | **モニタリング**として評価し、**改善を促す** |
| 株主 | 内部統制の責任は**ない** |
> 医者（監査人）は「塩分を控えて」とアドバイスまで。食生活を変えるのは本人（経営者）
- 内部統制の目的 — 業務の有効性・効率性、**報告の信頼性**（2023年の改訂で「財務報告」から広がった）、法令の遵守、資産の保全
@pair 監査 | 監査役 | 内部監査人 | 取締役の仕事を監視 ／ 内部統制を評価して改善を促す | M3

## IT統制の2種類 {{learning/応用情報技術者:05-2#内部統制}}
==業務処理統制＝システムの中、全般統制＝システムの周り==。
| 種類 | 何？ | 例 |
+| IT業務処理統制 | 業務システムの**中に組み込んだ**チェック | 入力データの正当性チェック、マイナスの金額は入れられない |
| IT全般統制 | システムが正しく動く**環境を守る**管理 | 開発・保守の手順、入退室管理、外部委託先の選定、FW の運用 |
> レジで例えると：業務処理統制＝**レジそのものの機能**、全般統制＝**レジを守るルール**（鍵・修理の手順・業者との契約）
@pair IT統制 | IT業務処理統制 | IT全般統制 | システムの中の機能 ／ システムの周りの管理 | M3
