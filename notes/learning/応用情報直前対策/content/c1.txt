## 署名と暗号化の鍵（★） {{learning/応用情報技術者:03-5#鍵の使い分け}}
==隠すなら受信者の鍵、証明するなら送信者の鍵==。署名は「送信者の秘密鍵で作り、送信者の公開鍵で検証」。
@fig keys | 誰の鍵で何をする？ | 上の段が「かける・作る」、下の段が「開ける・確かめる」
> 署名＝**実印**。押せるのは本人だけ（秘密鍵）、照らし合わせる印鑑証明（公開鍵）は誰でも見られる。暗号化＝**受信者しか開けられない鍵付きの箱**
( 署名の中身
+ 作る — 本文を**ハッシュ値**（要約）にして、**送信者の秘密鍵**で署名
+ 確かめる — **送信者の公開鍵**で署名からハッシュ値を取り出し、届いた本文から計算したハッシュ値と一致すれば**本人・改ざんなし**
+* 誰でも確かめられる — それで正しい。目的は**隠すことではなく証明**。偽物は秘密鍵がないと作れない
)
@fig signenc | 署名と暗号化を両方やる | 署名してから暗号化。実際は本文を共通鍵で暗号化し、その共通鍵だけを受信者の公開鍵で送る（ハイブリッド暗号。メールの S/MIME・PGP）
! 問題文が「**検証**」か「**作成**」かを先に見る。検証鍵＝送信者の**公開鍵**。「送信者の秘密鍵で暗号化して**内容を隠す**」は×（送信者の公開鍵は誰でも持つので誰でも開けられる）
@pair 鍵 | 署名 | 暗号化 | 送信者の鍵（秘密鍵で作り、公開鍵で検証）／ 受信者の鍵（公開鍵でかけ、秘密鍵で開ける） | S1

## 公開鍵暗号の中身（RSAと楕円曲線） {{learning/応用情報技術者:03-5#鍵の使い分け}}
どちらも公開鍵暗号で、**誰の鍵をどう使うかは同じ**。違うのは中の数学と鍵の長さ。
| | RSA | 楕円曲線（ECC） |
| 難しさの元 | **素因数分解** | **離散対数問題** |
+| 鍵の長さ | 長い（2048ビットなど） | **短い**（256ビットで RSA 3072ビット相当） |
| 向く所 | サーバ | スマホ・IoT・ICカード |
- ECDSA — 楕円曲線の**署名**
- ECDH — 楕円曲線の**鍵交換**（HTTPS の鍵決め）
> 錠前の**中の仕組み**が違うだけ。かけ方・開け方は同じ

## 証明書と失効（★） {{learning/応用情報技術者:03-5#証明書の失効}}
証明書は「この公開鍵は本人のもの」と **CA（認証局）が署名した身分証**。期限の前でも**失効**することがある（秘密鍵が盗まれた・会社がなくなった）ので、使う前に確かめる。
| 方法 | やり方 | 例えると |
| CRL | 失効した証明書の**リストを取って**自分で探す | ブラックリストの冊子 |
+| OCSP | 「この証明書は有効？」と**問い合わせて答えだけ**もらう | 電話で照会 |
( 選択肢に並ぶほかの用語
- LDAP — 社内の**名簿（ディレクトリ）**を調べる（389番）
- CHAP — PPP 接続の**チャレンジレスポンス認証**
- SNMP — 機器の**監視**（161・162番）
)
! 「名前に Certificate が入るのは OCSP だけ」は4択の中だけで通じる覚え方。**CRL**（Certificate Revocation List）にも入る。決め手は「**オンラインで失効を確認**」
! 主語のすり替え：「CA が利用者の秘密鍵を作る」は×。鍵ペアは利用者が作り、CA は公開鍵に**署名するだけ**
@pair 証明書 | OCSP | CRL | 問い合わせて答えだけもらう ／ 失効リストを丸ごと取って探す | S1

## チャレンジレスポンス {{learning/応用情報技術者:03-6#ログインの本人確認}}
==パスワードそのものは送らない==。サーバの**乱数（チャレンジ）**とパスワードから計算した**答え（レスポンス）**だけを送り、サーバも手元のパスワードで同じ計算をして照合する。
> 合言葉で例えると：門番「今日のお題は7」→ 合言葉と7で計算した「42」だけ答える。盗み聞きされても42しか漏れず、次はお題が変わる（**リプレイ攻撃**を防ぐ）
| 方式 | 毎回変わるもの | 要るもの |
+| チャレンジレスポンス | サーバの**乱数** | パスワードだけ |
| ワンタイムパスワード | **トークン**に出る数字 | トークン（機器・アプリ） |
- ワンタイムパスワードの作り方 — 時刻同期・カウンタ同期・チャレンジレスポンスの3つ。選択肢の「ワンタイムパスワード」はたいてい**トークンに出る数字**（時刻同期）
! 「固定パスワードを TLS で暗号化して送る」は暗号化通信の話（パスワードは**送っている**）。「端末のシリアル番号を送る」は毎回同じなので使い回される
@pair 本人確認 | チャレンジレスポンス | ワンタイムパスワード | サーバの乱数とパスワードを演算して送る ／ トークンに出る数字を入力 | S2

## シングルサインオン（★） {{learning/応用情報技術者:03-6#シングルサインオン}}
==1回ログインすれば、ほかのサービスにもパスワードなしで入れる==仕組み。方式は「誰が確かめて、何を持ち回るか」で分かれる。
| 方式 | 仕組み | 例えると |
+| リバースプロキシ型 | 利用者とWebサーバの間に**受付サーバ**を置き、全部の通信を中継 | コンシェルジュが全部代行 |
| エージェント型 | 各Webサーバの**エージェント**が Cookie を確かめる（Cookie が届く**同じドメインだけ**） | 施設ごとの係員が入館証を見る |

( リバースプロキシ型：誰が何を送る？
+ クライアント証明書 — **利用者のPC → リバースプロキシ**（本人確認のため）
+ 利用者IDなど — **リバースプロキシ → Webサーバ**（代わりにアクセス）
+ PC と Webサーバ — **直接はやりとりしない**
)
( SAML（サムエル）
+* SAML — 認証の結果を **XML** でやりとりして SSO を実現する仕様
+ IdP — **本人確認する係**（会社の Google アカウント）
+ SP — **使いたいサービス**（Slack・Notion）
+ アサーション — IdP が**署名した**「この人は確認済み」という表明（XML）。電子証明書（X.509）ではない
)
@steps SAML の流れ（遊園地のリストバンド）

SP がアサーションの署名を確かめる :: 本物なら入れる
別の SP（Notion）も同じように入れる :: これが SSO
@end
| 名前 | 何をする？ |
+| SAML | 認証の情報を交換して **SSO** |

## DNSとメールの2×2（★） {{learning/応用情報技術者:03-6#DNSとメールを守る}}
@mx なりすましを防ぐ4つ
x: デジタル署名で確かめる | 署名以外で確かめる
y: DNS を守る | メールを守る
TL: +DNSSEC :: DNS の**応答**に署名。キャッシュDNSサーバが公開鍵で検証
TR: ソースポートランダマイゼーション :: 問い合わせのポート番号を**毎回ランダム**にして偽の応答を当てにくく
BL: +DKIM :: **メール**に署名。公開鍵は送信元ドメインの DNS に置く
BR: SPF :: 送信元サーバの **IPアドレス**が DNS に登録したものか確かめる
@end
> 読み方：①「リソースレコード」「キャッシュサーバ」→ **DNS** の行、「電子メール」「メールサーバ」→ **メール**の行　②「公開鍵・秘密鍵・署名」→ **署名**の列
( DNSSEC の中身
+ 防ぐもの — **DNSキャッシュポイズニング**（偽の住所を覚えさせて偽サイトへ飛ばす）
+ 仕組み — 権威DNSサーバが応答に**秘密鍵で署名**、キャッシュDNSサーバが**公開鍵で検証**
+ 暗号化はしない — 中身は丸見えのまま。**確かめるだけ**
)
> DNSSEC＝**役所が出す証明書そのもの**に公印。DKIM＝**手紙に実印**、印鑑証明は役所（DNS）に置いておく
! DKIM も DNS を使うが、DNS は公開鍵を置く**棚**。署名される対象は**メール**。DNSSEC は **DNS の応答そのもの**に署名する
@pair 署名 | DKIM | DNSSEC | メールに署名（公開鍵はDNSに置く）／ DNSの応答に署名 | S3
@pair 送信元の確認 | SPF | DKIM | 送信元のIPアドレスで確かめる ／ メールの署名で確かめる | S3

## メール認証の4つ {{learning/応用情報技術者:03-6#DNSとメールを守る}}

## OP25Bと587番 {{learning/応用情報技術者:03-6#DNSとメールを守る}}
迷惑メール対策で、利用者が **25番で外のメールサーバへ直接送る**のを ISP が止める（**OP25B**）。代わりの正規ルートが **587番（サブミッションポート）**で、**SMTP-AUTH で認証した人だけ**が送れる。
| 番号 | 用途 |
| 25 | SMTP（サーバどうしの転送） |
+| 587 | サブミッション（利用者 → サーバ、**認証あり**） |
| 465 | SMTPS（TLS で暗号化した送信） |
| 110 ／ 143 | POP3 ／ IMAP（受信） |
> 25番＝誰でも使える**無人ポスト**（ばらまかれる）→ 封鎖。587番＝**身分証を見せる受付窓口**

## オープンリゾルバとオープンリレー {{learning/応用情報技術者:03-6#攻撃の手口}}

## 入口の3枚の壁（★） {{learning/応用情報技術者:03-5#入口を守る}}
外から **FW → IDS/IPS → WAF**。内側ほど中身を深く見るが、守れる範囲は狭く専門的になる（**多層防御**）。
| 壁 | 見るもの | できること | 例えると |
| FW | **IP・ポート番号** | 許可していない通信を遮断 | 門番 |
| IDS | 通信のパターン | 見つけて**通知だけ** | 監視カメラ |
| IPS | 同上 | 見つけて**遮断まで** | 警備員 |
+| WAF | **HTTP の中身** | SQLインジェクション・XSS・Web API への攻撃を遮断 | 荷物を開ける受付 |
> **D**etection＝見つける、**P**revention＝防ぐ
| 検知方式 | 仕組み | 弱み |
| シグネチャ型 | 既知の攻撃パターンと照合 | **未知**を見逃す |
| アノマリ型 | いつもと違う動きを検知 | **誤検知**が多い |
- フォールスポジティブ — 正常を攻撃と判定（**誤検知**）
- フォールスネガティブ — 攻撃を見逃す（**検知漏れ**）
! 3枚の壁の担当外：DNSキャッシュポイズニング → **DNSSEC**、メールボム → スパムフィルタ、第三者中継 → メールサーバで中継禁止。FW は**許可したポートの中**の攻撃（443番経由のSQLインジェクション）を防げない
@pair 入口の壁 | IDS | IPS | 見つけて通知だけ ／ 見つけて遮断まで | S4
@pair 入口の壁 | FW | WAF | IP・ポート番号で通す通さないを決める ／ HTTPの中身を見る | S4

@pair 見張る | SIEM | EDR | ログを集めて全体を分析 ／ 端末の上で検知・対応 | S4

## 起動とOSを守る（★） {{learning/応用情報技術者:03-6#起動を守る}}
+ TPM — PC に載った**セキュリティ専用チップ**（PC の中の金庫）。鍵の生成・保管、暗号処理。ハードなので鍵を盗み出されにくい（**耐タンパ性**）
+ セキュアブート — 起動時にブートローダや OS の**デジタル署名を確かめ**、偽物なら起動しない。**UEFI** の機能。OS より先に動く**ブートキット**を防ぐ
> 搭乗前の**パスポートチェック**。ウイルス対策ソフトは飛行中の警備（もう乗ってしまった後）
- BIOS ／ UEFI — 電源を入れて最初に動くファームウェア。UEFI が後継
- BIOS・HDDパスワード — **人**をパスワードで確かめる（セキュアブートは**プログラム**を署名で確かめる）
( セキュアOS（root を乗っ取られても被害を小さく）
+ 最小特権 — 管理者の権限を**必要な分だけ**に小分けする
+ 強制アクセス制御（MAC） — システム全体のルールで決め、**管理者でも変えられない**。例 SELinux
- 任意アクセス制御（DAC） — ファイルの**持ち主**が自由に決める（ふつうのOS。root は何でもできる）
)
> 社長の鍵1本で全部の部屋が開く（ふつうのOS）か、**社長でも入れない部屋**がある（セキュアOS）か
@pair 起動を守る | TPM | セキュアブート | 鍵をしまう専用チップ ／ 起動時に署名を確かめる仕組み | S4

## 攻撃の手口 {{learning/応用情報技術者:03-6#攻撃の手口}}
+ ボットとC&Cサーバ — 乗っ取った PC（ボット）の集団に**指令を出す司令塔**が C&C サーバ。ボットの方から「次の命令は？」と問い合わせる（**コネクトバック通信**。内から外への通信は FW を通りやすい）
+ サイドチャネル攻撃 — 暗号を正面から解かず、**消費電力・処理時間・電磁波・故障時の誤り**から鍵を推測する
- 差分解読・線形解読・総当たり — **数学・計算**で解く方
+ エクスプロイトコード — **脆弱性を突く**プログラム。攻撃にも、脆弱性が本当にあるかの確認にも使う
> サイドチャネル＝金庫のダイヤルの**音**を聞く。exploit＝つけ込む
| 似た名前 | 一言で |
+| エクスプロイトコード | 脆弱性を**悪用**する |
| MAC（メッセージ認証符号） | **改ざん**を見つける |
| シグネチャコード | マルウェアを**見分ける特徴** |
| ワンタイムパスワード | ログインのたびに**変わる** |
@pair 攻撃 | サイドチャネル攻撃 | 総当たり攻撃 | 電力・時間・電磁波など物理の情報から推測 ／ 鍵を全部試す | S4

## 無線LANを守る {{learning/応用情報技術者:03-5#無線LANを守る}}
| 機能 | 一言で | 注意 |
| MACフィルタ | 登録した機器だけつなぐ | MAC を偽装されると無力 |
| SSIDステルス | ネットワーク名を見せない | **暗号化ではない** |
+| プライバシーセパレータ | **利用者どうしの通信を禁止** | 子機 → インターネットは通る |
| WPA2・WPA3 | 通信を**暗号化** | 危ないサイトのブロックはしない |
| WPS | 接続設定を**ボタン1つ**で | 守る機能ではない |
> プライバシーセパレータ＝カフェで**隣の人のPCを覗けない**

## CSIRTとSOC（★） {{learning/応用情報技術者:03-6#攻撃の段取りと社会の仕組み}}
==SOC が見張って、CSIRT が対応する==。SOC は**24時間見張って**異常を CSIRT へ渡す（ビルの警備室）。対応チームは「**誰のために動くか**」で6種類（WHOIS の技術連絡担当はドメインの問い合わせ窓口で、対応チームではない）。
| 誰のため | 種類 | 一言で |
| 自社 | 組織内CSIRT | 社内の事件に対応（社内の消防隊） |
+| 自社製品の利用者 | **PSIRT** | 製品の脆弱性を直してパッチを出す（メーカーのリコール班） |
| 国 | 国際連携CSIRT | 国の代表として海外と連絡（JPCERT/CC） |
+| ほかのCSIRT | **コーディネーションセンター** | CSIRT どうしの**連携・調整役** |
| 世の中 | 分析センター | 攻撃の傾向分析・注意喚起 |
| お客さん（有償） | インシデントレスポンスプロバイダ | CSIRT の仕事を**お金をもらって代行** |
> **C**SIRT＝**C**omputer（社内）、**P**SIRT＝**P**roduct（製品）
@pair 対応チーム | CSIRT | PSIRT | 自社の組織・システムの事件 ／ 自社が売る製品の脆弱性 | S4

## 脆弱性の名札 {{learning/応用情報技術者:03-6#脆弱性の名札}}
頭の C は **Common（共通）**。2文字目からの英単語で何の名札か決まる。
| 略称 | 何に名札？ | 手がかり |
+| CVE | **個別の脆弱性**（事件番号） | **V**ulnerability |
+| CWE | 脆弱性の**種類**（手口の分類） | **W**eakness |
| CCE | セキュリティの**設定項目** | **C**onfiguration |
| CPE | **製品**（OS・アプリ・機器） | **P**latform |
+| CVSS | **深刻度の点数**（0.0〜10.0） | **S**coring |
- SCAP — 上をまとめて自動化する仕組み。中身は CVE・CCE・CPE・CVSS＋検査用の言語（**CWE は入らない**）
+ JVN — 日本向けの脆弱性情報と**対策**を公開するサイト（JPCERT/CC と IPA）
- MyJVN — 自分の PC のソフトが古くないか**調べるツール**
> Log4j の例：CPE＝Apache Log4j、CVE-2021-44228（事件番号）、CVSS 10.0（最悪）。CWE は「SQLインジェクション」のような手口の種類の番号
@pair 名札 | CVE | CWE | 個別の脆弱性の番号 ／ 脆弱性の種類の番号 | S4
@pair 名札 | JVN | MyJVN | 脆弱性情報と対策を公開するサイト ／ 自分の環境を調べるツール | S4
