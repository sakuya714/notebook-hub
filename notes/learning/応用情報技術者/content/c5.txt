## スケジュール
@fig cpm | アローダイアグラム（数字は 最早/最遅） | B→E→Gがクリティカルパス（14日）。Hの前の④は1日余裕あり
(
-* クリティカルパス — 一番長い経路＝全体の日数を決める。1日遅れたら全体も遅れる
+ 最早結合点時刻 — 前から計算、合流点は**最大**
+ 最遅結合点時刻 — 後ろから計算、分岐点は**最小**
- ダミー作業 — 点線。0日、順番だけ表す
+ トータルフロート — 全体を遅らせずにずらせる日数（クリティカルパス上は0）
- ガントチャート — 予定と実績は見やすいが、**作業のつながりは描けない**
+* PDM — 作業を箱で。FS（終→始）・SS（始→始）・FF・SF。**リード＝前倒し、ラグ＝遅らせる**
+ クリティカルチェーン — 資源（人・設備）の取り合いも考える。バッファは最後と合流点にまとめて置く
)
= #+ 三点見積り
= (悲観値 ＋ 4 × 最頻値 ＋ 楽観値) ÷ 6
=   例）(14＋24＋4)÷6 ＝ 7日
@fig crash | クラッシングとファストトラッキング | どちらもクリティカルパスを縮めて、完了予定日に間に合わせる
( 期間を縮める
-* クラッシング — **資源を追加**して縮める（残業・詳しい人を増員）。お金がかかる
-* ファストトラッキング — 順番の作業を**並行**させる（設計が終わる前に、固まった所から開発）。手戻りリスク
+ 縮める作業 — **クリティカルパス上**で費用増加率が一番安いものから1日ずつ。縮めたらパスを確認し直す
)

## コスト（EVM）
@fig evm | EVM：全部お金で比べる
= #+ EVM
= SV ＝ EV − PV（マイナスなら遅れ）
= SPI ＝ EV ÷ PV（1未満なら遅れ）
= CV ＝ EV − AC（マイナスなら予算超過）
= CPI ＝ EV ÷ AC（1未満なら超過）
= EAC（完成時総コスト）＝ AC ＋ (BAC − EV) ÷ CPI
= ETC（残り）＝ EAC − AC
= VAC ＝ BAC − EAC
= 例）BAC100・PV50・EV40・AC60 → CPI＝2/3 → EAC＝60＋60×3/2＝150
> どの式もEVが先頭。相手がPV（予定）ならスケジュール、AC（払ったお金）ならコスト
! EACの計算に**PVは使わない**（ひっかけで置いてある数字）。「残りは計画どおり」なら EAC ＝ AC ＋ (BAC − EV)
(
+ トレンドチャート — 予定線より左上＝進んでるけど費用超過、右下＝遅れてるけど費用は下回り
)

## 見積り
(
+* ファンクションポイント法 — 外部入力・外部出力・内部論理ファイル・外部インタフェースファイル・外部照会を数えて重み付け。**言語に依存しない・初期から使える**
+* COCOMO — **プログラムの行数**（KLOC）＋補正係数で工数を出す
+ 標準タスク法 — WBSごとに積み上げ（ボトムアップ）
+ デルファイ法 — 専門家へ匿名アンケートを繰り返して収束
+ 規模と工数 — 規模が大きいほど工数は**指数関数的**に増え、生産性は下がる
+* ブルックスの法則 — 遅れてるプロジェクトに人を足すと**もっと遅れる**
)
= #+ 生産性・人数
= 全体の生産性 ＝ 1 ÷ (1/X ＋ 1/Y ＋ 1/Z)
=   ← 工程ごとの生産性を単純平均しちゃダメ
= コミュニケーションの経路数 ＝ n(n−1) ÷ 2
=   （5人→10、10人→45）
= 期間 ＝ 工数（人月）÷ 人数

## 事業継続（BIA・BCP）
(
+* BIA — 業務が止まったときの影響を分析し、**優先して復旧する業務と目標**（RPO・RTO・RLO）を決める（BCPの前段）
+ BCP — 事業継続計画。災害が起きたら**どう動くか**を決めた計画
+ ホットサイト／コールドサイト — すぐ切り替えられる代替施設／設備だけで立ち上げに時間がかかる
)
| 目標 | 決めること | ラーメン屋が火事なら |
| RPO | **いつの時点**のデータまで戻すか（**P**oint＝時点） | 昨日の閉店時点のデータまで |
| RTO | **何時間で**再開するか（**T**ime＝時間） | 3日以内に営業再開 |
+| RLO | **どこまでの水準**で再開するか（**L**evel＝レベル） | まずラーメン1種類だけ |
BCPを発動したら、4つのフェーズで元の状態に戻していく
@flow BCP発動::初動対応 > 業務再開::代替手段で最低限 > +業務回復::再開する範囲を広げる > +全面復旧::通常運用に戻す || BCPの4フェーズ。ラーメン屋なら 避難・消火 → キッチンカー → メニューを増やす → 元の店舗

## システム監査
@flow 体制づくり::監査チーム > 監査計画::何をいつ・進捗管理 > 予備調査::ざっと実態をつかむ > 本調査（監査手続）::監査証拠を集める・監査調書 > 評価・結論 > 監査報告書::保証意見 or 指摘事項＋改善勧告 > フォローアップ::改善状況を確認 || 監査人は独立した第三者
> 健康診断で：計画＝検査の予定、予備調査＝**問診**、本調査＝**血液検査・レントゲン**（証拠集め）、報告＝**診断結果を伝える**、フォローアップ＝**再検査**
| 技法（人が調べる） | 何をする |
| チェックリスト法 | 質問リストに**回答してもらう** |
| ドキュメントレビュー法 | **資料を読んで**確かめる |
| インタビュー法 | **担当者に聞く** |
| 現場調査法 | **現場に行って見る** |
+| 突合・照合法 | 記録同士を**突き合わせる**（伝票とデータが一致するか） |
+| ウォークスルー法 | データの発生から活用まで**追跡**する |

| 技法（コンピュータを使う） | 何をする |
+| CAAT | **ツール**でデータを分析する（コンピュータ支援監査技法） |
+| テストデータ法 | 監査人が**データ**を用意して流す |
+| 並行シミュレーション法 | 監査人が**プログラム**を用意して結果を比べる |
+| 監査モジュール法 | 監査用の機能を対象プログラムに組み込む |
(
+* 監査手続 — 監査項目について**十分かつ適切な証拠**を入手するための手順
+ システム監査基準／システム管理基準 — 監査人がどう監査するか／監査対象がどうあるべきか
+* 監査人がやらないこと — 改善の**指示・参加・実施**（自分で直すと**独立性**を失う）。やるのは評価・報告・**改善の勧告**・フォローアップまで
+ 指摘事項 — 監査対象と意見交換して事実確認してから書く
+ 監査証拠 — ログ・承認記録など客観的な記録ほど強い（ヒアリングだけだと弱い）
+* 外観上／精神上の独立性 — 監査対象と**利害関係がない**／公正な判断を貫く
+ 監査報告書の宛先 — 監査の**依頼者**（経営者など）。保証型＝適切だと保証、助言型＝改善を助言
)

## 内部統制（会社の中のルールとチェック）
| 人 | 内部統制での役割 |
+| 経営者 | 内部統制を**整備・運用**する。**最終的な責任**を持つ |
| 取締役会 | 内部統制の**基本方針を決める**。経営者を監督する |
| 監査役 | 取締役の仕事の監査の一環で、**独立した立場**から内部統制を**監視・検証** |
+| 内部監査人 | **モニタリング**の一環で、内部統制を**検討・評価**し**改善を促す** |
| 株主 | 内部統制の役割・責任は**ない** |
( 内部統制とガバナンス
- 内部統制 — 会社の中のルールとチェック体制。業務に組み込み、**組織の全員**で動かす
- コーポレートガバナンス — ステークホルダが企業活動を監視
+ ITガバナンス — **経営陣**がITを評価・指示・モニタ（JIS Q 38500）
)
( 統制のやり方（ITと職務分掌）
+ IT全般統制 — 開発・変更・アクセス・運用の管理
+ IT業務処理統制 — 入力チェックなど業務システムの中のチェック
-* 職務分掌 — 権限を分けて互いにけん制（発注する人と承認する人を分ける）
)
( 内部統制の中身と法律
+ 内部統制の4つの目的 — 業務の有効性・効率性／**報告**の信頼性（財務報告を含む。2023年改訂）／法令遵守／資産の保全
+ 6つの基本的要素 — 統制環境・リスクの評価と対応・統制活動・情報と伝達・モニタリング・**ITへの対応**
+ J-SOX — 上場企業に**内部統制報告書**と監査法人の監査を義務付け（金融商品取引法）
)
