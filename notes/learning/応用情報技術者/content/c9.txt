## 基礎理論・コンピュータ構成要素
@card クロスコンパイラとエミュレータ | 01-1#コンパイラ
| | クロスコンパイラ | エミュレータ |
| やること | 別の環境用の**実行ファイルを作る**（翻訳する） | 別の環境の**ふりをして実行**する |
| 動かす場所 | **相手の環境**（ここでは動かさない） | **その場**で動く |
| 例 | Mac 上で組込み機器用・iPhone 用のアプリをビルド | Mac 上で Android や昔のゲーム機を動かす |
| 料理で | 日本の厨房で、アメリカ家庭用のレシピに**書き直す**人（ここでは食べない） | 厨房をアメリカのキッチン**そっくりに再現**して、ここで作る |
> 判定のコツ：結果が「**ファイル**」か「**動作**」か。クロスコンパイラは**実行ファイルができる**（動かすのは相手の環境＝組込み機器など）、エミュレータは**自分のPCの上でその場で動く**
> Mac で：クロスコンパイラ＝Mac で iPhone 用アプリを**ビルド**して、できたファイルを **iPhone に入れて動かす**。エミュレータ＝Mac の画面の中で別の機械のプログラムが動く（Android エミュレータなど。Xcode の iPhone シミュレータは Mac 用に作ったアプリを動かす仕組みで、厳密にはエミュレータとは別物）
(
+ クロスコンパイラ — 「〜向けに**実行ファイルを生成**」（**Cross＝またがる**：作る場所と動く場所が違う）
+ エミュレータ — 「挙動を**模倣**」「**疑似的に実行**」（**Emulate＝真似る**）
- プログラムジェネレータ — 条件を入れると**プログラムを自動生成**
- 最適化コンパイラ — コードを**速く・小さく**なるように変換
)
@end

@card ホモジニアスとヘテロジニアス（マルチコア） | 02-1#CPUを速くする
| 名前 | 意味 | コア |
| ホモジニアス | **同じ** | **同じ種類**のコアだけ |

(
+ ヘテロ — 「**特徴の異なる**」「**高性能コア＋省電力コア**」「**CPU＋GPU**」
)
> 覚え方（どっちか1つでOK）：**ヘテロ＝ヘンテコな組み合わせ**（違うもの同士を混ぜる）／英語で **homo＝same（同じ）、hetero＝different（違う）**

@card フラッシュメモリの寿命（ウェアレベリング） | 02-1#メモリ
フラッシュメモリ（SSD・USBメモリ）は**同じ場所に何回も書くと壊れる** → 書き込む場所を全体に**散らして平均的にすり減らす**のがウェアレベリング。消しゴムの同じ角ばかり使うとすぐダメになる、**全部の角を順番に使えば長持ち**
(
+ ウェアレベリング — 書込みを**均等に分散** → 寿命を**延ばす**
+ ライトアンプリフィケーション — 頼んだ量より**余計に書き込んでしまう**現象（書込み増幅）→ 寿命を**縮める**（悪い方）
- デフラグ — **HDD**でバラバラのデータを**並べ直して**速くする → 寿命とは関係なし（SSDには不要）
+ ジャーナリング — ファイルの変更を**ログに記録**して、障害時に復旧しやすくする → 寿命とは関係なし
)
( フラッシュメモリの基本（不揮発）
+ NAND型 — **ページ単位**で読み書き。安くて大容量 → SSD・USBメモリ
+ NOR型 — **バイト単位**。読出しが速い → ファームウェア
+ SLC／MLC／TLC／QLC — 1セルに 1／2／3／4 ビット（多いほど大容量だが寿命は短い）
)
> **Wear＝すり減る、Leveling＝平らにならす**。「フラッシュメモリ」「書換え回数」「寿命を延ばす」→ ウェアレベリング
@end

## システム構成・OS・ハードウェア
@card 仮想化の3方式（ホスト型・ハイパバイザ型・コンテナ型） | 02-2#仮想化
**サーバ仮想化**＝1台の物理サーバで**複数のサーバOS**を動かすこと（VMware・Xen）。方式は3つで、違いは「**何の上に仮想マシンを乗せるか**」だけ。**下から積み上げ**で見る
@fig virt | 3つの仮想化（下から積む） | オレンジが仮想化の土台。コンテナ型だけゲストOSがない
| 種類 | 仕組み・速さ | 例 |
| ホスト型 | ふつうのOS（ホストOS）の上に**仮想化ソフト**。**OSが2重**で遅い | VirtualBox・QEMU |
| ハイパバイザ型 | ハードの上に**直接**仮想化ソフト。速い | Xen・KVM・VMware ESXi |
+| コンテナ型 | ホストOSを**共有**、ゲストOSなし。**一番軽い・速い** | **Docker** |
( 用語
- ホストOS — 実際のPCに**最初から入ってる**OS（Mac なら macOS）
- ゲストOS — 仮想マシンの**中で動かす**OS（Mac 上で動かす Windows など）
+ ハイパバイザ（ハイパーバイザ） — ホストOSなしで、**ハードの上に直接乗る仮想化専用ソフト**
+ コンテナ — OSを丸ごと用意せず、**ホストOSを共有**してアプリだけ隔離
)
> マンションで：ホスト型＝家の中に**もう1軒プレハブを建てる**（重い）／ハイパバイザ型＝土地に**直接マンションを建てて部屋を分ける**／コンテナ型＝**シェアハウス**（キッチン・水回り＝OSは共有、部屋＝アプリだけ個別）
( 見分け方
+ コンテナ型 — 「**ゲストOSが不要**」「**OSを共有**」「**軽量**」
+ ハイパバイザ型 — 「**ハードウェア上で直接動作**」
+ ホスト型 — 「**ホストOS上で動作**」
)
( 同じ節に出る言葉
+ ライブマイグレーション — 仮想サーバを**止めずに**別の物理サーバへ移す
+ サーバコンソリデーション — 物理サーバを集約 → 管理コスト減
+ マルチテナント — 1つの環境を複数の利用者で共有しつつ分離
+ シンプロビジョニング — 見せるのは要求量、物理は**使った分だけ**割り当て
+ ストレージ自動階層化 — よく使うデータは速い層、あまり使わないのは遅い層へ自動で移す
)
@end

@card IaCとプロビジョニングツール | 02-2#仮想化
**IaC**（Infrastructure as Code）＝サーバやネットワークの**設定をコード（ファイル）に書いて、自動で構築する**やり方（**考え方**）。**プロビジョニングツール**＝それを実際にやる**道具**
| | 従来 | IaC |
| やり方 | **手順書を見ながら手作業**で設定 | **コードを実行**すると自動で設定 |
| ミス | 人によって設定がズレる | **毎回同じ**環境ができる |
| 同じ環境をもう1つ | また手作業 | **コードを流すだけ** |
| 変更履歴 | 残りにくい | **Gitで管理**できる |
> 料理で：従来＝毎回**シェフが記憶で**作る（日によって味がブレる）／IaC＝**レシピを機械に読ませて**自動調理（毎回同じ味、何台でも同時に）
( プロビジョニング
+ プロビジョニング — サーバを**使える状態に準備する**こと（OS・ソフトのインストール、設定、アカウント作成など）
+ プロビジョニングツール — その準備を、**設定ファイルに書いた通りに自動で**やってくれる道具
+ 代表的なツール — **Terraform**・AWS CloudFormation・Ansible
)
> 新しいPCで：手作業＝新しい Mac を買って、アプリを1個ずつ入れて、設定を1つずつ変える／プロビジョニングツール＝「**入れるアプリと設定のリスト**」を渡したら**全部自動**でやってくれる → 100台でも同じ状態にできる
| サーバ管理ツール | 目的 |
| パフォーマンス監視 | 性能を**見張る** |
| 構成管理 | 入ってるソフトを**一覧管理** |
+| プロビジョニング | 記述どおりに**自動で構築** |
| 死活監視（サーバ監視） | 動いてるか**外から確認** |
( 見分け方
+ IaC — 「**インフラの設定をコードで記述**」「**自動化**」「**手作業を減らす**」
+ プロビジョニング — 「**あらかじめ記述**」「**自動的に構成**」（＝IaCの道具）
)
> 名前そのまま：**Infrastructure（土台）を Code（コード）として**扱う＝IaC／**Provision＝準備・支給する**：サーバに必要なものを**自動で支給**
@end

@card 仮想記憶（ページング〜LRU） | 02-3#仮想記憶
全部「**メモリ管理**」の話で、**1つの流れ**でつながっている。**勉強机**で例える：主記憶（メモリ）＝**勉強机**（狭いけどすぐ使える）、ディスク＝**本棚**（広いけど取りに行くのが遅い）、プログラム＝**教科書**
1. **仮想記憶**：机が狭くても、**本棚も机の一部みたいに**使う。必要なページだけ机に出す
2. **ページング／セグメンテーション**：机への置き方を決める
3. **ページテーブル**：どこに置いたかの**台帳**で場所を管理
4. **ページフォールト**：使いたいページが**机にない**（本棚にある）
5. **ページ置換え（LRU など）**：机が満杯なら、何を片付けるか決める
6. **フラグメンテーション**：置き方次第で、空きがバラバラになる
7. **ガーベジコレクション**：使い終わったメモリを自動で回収（ページの話とは**別**）
| 置き方 | 区切り方 | 弱点 |
| ページング | **同じサイズ**（固定長）。全部**同じ大きさのファイル**に分けて置く | 最後のファイルが余る（**内部断片化**） |
| セグメンテーション | **意味のまとまり**（可変長）。「数学」「英語」と**バラバラの大きさ**で置く | 隙間ができる（**外部断片化**） |
( 台帳と「机にない！」
+ ページテーブル — 「このページは机のどこ？本棚？」を記録した**台帳**。**MMU** がこれで仮想アドレス → 実アドレスに変換
+ 多段ページテーブル — 台帳を**必要な分だけ**作る → **全ページ分の台帳は要らない**
+ TLB — アドレス変換の結果を覚えておく**専用キャッシュ**（毎回台帳を見に行かない）
+ ページフォールト — 使いたいページが**主記憶にない**状態（割込みが起きる）
+ フォールト時の順番 — フォールト → 片付けるページを決める → 片付けて（**ページアウト**）→ 本棚から持ってくる（**ページイン**）
+ デマンドページング — フォールトしてから読む。プリページング＝先読み
)
| 置換え | 片付けるページ |
| FIFO | **一番最初に置いた**もの |
+| LRU | **一番長く使ってない**もの（Least Recently Used） |
| LFU | **使った回数が一番少ない**もの（Least Frequently Used） |
> LRU・FIFO の置換え回数は、**表を描いて1つずつ埋める**。頭の中だけだとほぼ間違える
( 断片化と回収
+ フラグメンテーション（断片化） — **空きはあるのに、バラバラで使えない**状態。**セグメンテーション**で起きやすい（大きさがバラバラだから）
+ コンパクション — 使ってる物を**端に寄せて**空きをまとめる（断片化の対策）
+ ガーベジコレクション（GC） — プログラムが**使い終わったメモリを自動で回収**する機能（Java・JavaScript など）。**机に散らかったゴミを自動で捨てる係**
+ スラッシング — メモリ不足で**ページ置換えが多発**して激遅（CPU 使用率↓・ディスク I/O↑）
)
( 計算
- ページテーブルの大きさ — 2^(L−N) × 2^E（仮想空間 2^L・ページ 2^N・1項目 2^E バイト）
- 平均アクセス時間 — 主記憶時間 ＋ フォールト処理時間 × フォールト率（単位をそろえる）
)
> つながりを1行で：**仮想記憶**で机を広く見せる → **ページング／セグメンテーション**で置き方を決める → **ページテーブル**で場所を管理 → 机にないと**ページフォールト** → **LRU など**で片付ける物を決める → 置き方次第で**断片化** → 不要なメモリは **GC** が回収
! **ページングでは外部断片化は起きない**（固定長だから）。**GC はページフォールトと無関係**（プログラムのメモリの後片付け）
@end

@card OSの中身とLinux | 02-3#OSの中身とUNIX・Linux
**Linux は厳密には「カーネル（OSの心臓部）」だけ**のこと。普段「Linux という OS」と呼んでいるのは、カーネルに道具を足して完成させた**ディストリビューション**（Ubuntu など）
| 層 | 中身 | 家で例えると |
| アプリ | ブラウザ・Word・ゲーム | **家具・家電** |
| OS | Windows・macOS・Linux・iOS | **電気・水道・管理人** |
| ハードウェア | CPU・GPU・メモリ・ストレージ | **土地・建物** |
アプリはハードを直接いじらず、**OS にお願いして**使わせてもらう
( ハードウェアの用語
- LSI — Large Scale Integration（大規模集積回路）。**チップそのもの**（入れ物）。CPU も GPU も LSI の一種
- CPU — Central Processing Unit。**何でも計算する頭脳**。細かい処理を順番にこなす
- GPU — Graphics Processing Unit。**単純な計算を大量に同時**にやる係（画像・AI 向き）
+ SoC — System on a Chip。CPU・GPU・メモリなどを**1つの LSI にまとめた**もの（M1 など）
- CPI — Cycles Per Instruction。1命令に何クロックかかるか（**小さいほど速い**）。**性能の指標**で部品ではない
)
( OSの中身
+ カーネル — メモリ・プロセス・ファイル・デバイスの**管理**（OSの心臓）。例：**Linux カーネル**
+ シェル — 人の**コマンドを受け取る**窓口（CUI）。Bash・zsh
+ ライブラリ — アプリが使う**共通の道具箱**。glibc
+ GUI — **マウスで操作**できる画面。GNOME・KDE
+ デーモン — 常駐してバックグラウンドで動くプロセス
)
! カーネルの仕事は**プロセス・メモリ管理**など。GUI・シェル・ブラウザなどのアプリは**カーネルの仕事ではない**
( UNIX と Linux の家系図
- UNIX — 1969年の**元祖**のOS
+ BSD系 — UNIX の血を引く → **macOS・iOS**
+ Linux — UNIX を**真似て一から作った**「UNIX風」のOS → Ubuntu・**Android**（中身は Linux カーネル）・サーバの大半
- Windows — UNIX とは**別系統**
)
> 覚え方：**LSI＝チップ（入れ物）、CPU/GPU＝中の計算係、CPI＝速さの指標**／**カーネル＝OSの心臓、Linux＝そのカーネルの名前**／**UNIX が元祖、Linux は真似っ子、macOS は子孫、Windows は他人**。Mac で `uname -a` を打つと出る「Darwin」が macOS のカーネル名
@end

@card OSSとライセンス（GPL・LGPL・MIT…） | 02-3#OSS
**OSS**（Open Source Software：オープンソースソフトウェア）＝**ソースコードが公開**されていて、**ライセンスの条件を守れば、誰でも利用・改変・再配布できる**ソフトウェア
| よくある誤解 | 正しくは |
| 無料でないといけない | **有料で販売してもよい** |
| 作者は著作権を放棄している | **著作権は作者にある**。ライセンスで利用を許可しているだけ |
| 作者が品質を保証してくれる | **無保証**が原則 |
+| 商用利用禁止などの制限をつけてよい | 利用者・用途を**差別・制限してはいけない**（差別の禁止） |
ライセンスは「改変したものを**配布するとき**、ソースコードを公開する義務があるか」で3つに分かれる
| ライセンス | 型 | 公開する範囲 |
| GPL | **コピーレフト型** | 改変・組み込んだプログラム**全体**のソースを、**同じライセンス**で公開 |
+| LGPL・MPL | **準コピーレフト型** | 改変した**OSSの部分だけ**公開（自作部分は公開不要） |
| MIT・BSD・Apache | **非コピーレフト型** | 公開義務**なし**（著作権表示・ライセンス文を残せばOK）。自社製品に入れて非公開にしてもよい |
( 細かい違い（試験ではここまで問われない）
+ LGPL — ライブラリ（OSS部分）を改変したら**その部分を公開**。ライブラリを**使うだけのアプリ**は公開不要
+ MPL — **ファイル単位**。改変したファイルだけ公開
+* AGPL — GNU Affero GPL。**ネット経由でサービスとして提供するだけ**でも公開義務が出る
)
( 公開義務のポイント
+* 公開義務が出るとき — **配布するとき**だけ。**社内だけで使う・サーバ上で動かすだけ**なら GPL でも公開義務なし（**AGPL は例外**）
+ 製品に組み込みやすい — **非コピーレフト型**（自社のソースを出さなくていい）
)
| 分野 | 代表的なOSS |
| OS | Linux |
| Webサーバ | Apache HTTP Server・Nginx |
| データベース | MySQL・PostgreSQL |
| 言語の処理系 | CPython（Python）・PHP・Ruby・Node.js・OpenJDK（Java） |
| ブラウザ | Firefox・Chromium |
| オフィスソフト | LibreOffice |
| 開発ツール | Git |
| 仮想化・コンテナ | **Docker Engine**・KVM・Xen |
| ライブラリ | React（MIT） |
> MySQL は「GPL と商用ライセンスの**デュアルライセンス**」だけど、**OSS として扱ってOK**
! Docker は**全部が OSS ではない**：**Docker Engine**（中心の部分）は OSS（Apache 2.0）、**Docker Desktop**（Mac・Windows 用アプリ）は **OSS ではない**（大企業は有料）
( 見分け方（問題文の言葉 → 答え）
+ GPL — 「改変したプログラム**全体**のソース公開が必要」
+ MIT・BSD・Apache — 「**著作権表示のみ**でよく、ソース公開は不要」
+ OSSの定義に反する — 「利用者や用途を**制限**する」
+ 誤り — 「著作権を**放棄**している」→ それは**パブリックドメイン**（OSSとは別の考え方）
)
@end

@card 3DCGの技法 | 02-4#＋α 3DCG・VR・AR
3DCG の技法は**キーワード1語**で見分けられる。役割で5つに分けて覚える
( ① 光・影をつける
+ レイトレーシング — 目（視点）から光の経路を**逆にたどって**、反射・屈折・透過を計算。「**視線追跡**」「反射・屈折」「鏡面」
+ ラジオシティ法 — 面と面の間で光が**何度も跳ね返る**のを計算（やわらかい間接光）。「**拡散反射面の相互反射**」
+ レイキャスティング — 視線を**飛ばすだけ**。反射・透過は**追わない**（簡易版）
- シェーディング — 光の当たり方で**陰影**をつける。「陰影」「明るさ」
)
( ② 見えない面を消す（陰面消去）
+ Zバッファ法 — 画素ごとに**一番手前の物**だけ描く。「**奥行き（Z値）**」「画素ごとに奥行きの最小値を保持」
)
( ③ 表面の見た目をつける
+ テクスチャマッピング — 表面に**画像（模様）を貼る**。「模様を**張り付ける**」「壁紙」
+ バンプマッピング — 表面に**凹凸があるように見せる**。「**凹凸**」
)
( ④ 形を作る（モデリング）
- ポリゴン — **小さな多角形の組合せ**で形を作る。「多角形」
+ メタボール — **球の集まり**で、なめらかな形を作る。「球・楕円体」「**滑らか**」
- ワイヤーフレーム — **線だけ**で形を表す。「線」「骨組み」
)
( ⑤ 仕上げ
+ アンチエイリアシング — 斜め線の**ギザギザをなめらか**にする。「ギザギザ」「**ジャギー**」
+ レンダリング — 全部まとめて**画像として描く**（最後の工程）。「描画」「画像に変換」
+ ボリュームレンダリング — **空間中のデータ**（CT・MRI など）から明るさを計算して描く。反射・透過は追わない
)
> 覚え方：**レイ＝光線**。トレーシング（**追う**）なら反射まで、キャスティング（**投げる**）なら投げるだけ。**ラジオシティ＝光の跳ね返り合い**
( 見分け方（よく出る説明文）
+ テクスチャマッピング — 「物体の表面に、別に定義された**模様を張り付ける**」
+ レイトレーシング法 — 「視線と物体の交点のうち**視点に最も近い交点**を選ぶ」（視線をたどって隠面消去する使い方）
+ Zバッファ法 — 「画素ごとに**奥行き（距離）の最小値**を保持」
+ ラジオシティ法 — 「**拡散反射面間の相互反射**を考慮」
+ ボリュームレンダリング — 「反射・透過方向の追跡を**行わず**、**空間中のデータ**から輝度を計算」（視線を投げるだけ＝レイキャスティングで描く）
)
! 選択肢は**説明と名前がシャッフル**される（「レイトレーシング法は模様を張り付ける」など）。名前ではなく**説明文のキーワード**から技法を決めて、名前と合っているかを見る
@end

@card VR・ARの4つの処理 | 02-4#＋α 3DCG・VR・AR
VR ゲームを作る流れの順に4つ。覚え方は「**追う → 動かす → 合わせる → 描く**」
| 順 | 名前 | 何をする？ | キーワード |
| 1 | **トラッキング**（Tracking） | カメラ・センサーで**人の動きを追う** | **ウェアラブルカメラ・慣性センサー**、非言語情報を認識 |
| 2 | **モデリング変換** | 物を**物理法則で動かす**（時間とともに変化） | **時間経過・物理法則** |
| 3 | **幾何学的レジストレーション**（Registration） | **現実と仮想の座標を一致**させる（AR用） | **現実と仮想を融合・3次元座標を一致** |
| 4 | **レンダリング**（Rendering） | 最後に**画面に映る画像を作る** | **ディスプレイに描画できる画像に変換** |
> ポケモンGOで：①スマホの向きや動きを**センサーで検知**（トラッキング）②ポケモンが**跳ねたり動いたり**（モデリング変換）③ポケモンを**現実の地面の上にピタッと置く**（レジストレーション）④それを**画面の絵**として描く（レンダリング）
( 見分け方（1語で）
+ トラッキング — 「**センサー・カメラ**」
+ モデリング変換 — 「**物理法則・時間経過**」
+ 幾何学的レジストレーション — 「**現実と仮想を一致**」
+ レンダリング — 「**画像に変換・描画**」
)
( 一緒に出る
+ VR／AR／MR — 仮想に入る／現実に重ねる／現実と仮想が相互に作用
+ レイトレーシング — 光線を追って描くレンダリングの方法。テクスチャマッピング＝表面に模様、アンチエイリアシング＝ギザギザを消す（全部は「3DCGの技法」のカード）
)
@end

## データベース・ネットワーク
@card キーの種類 | 03-1#キーの種類
例：社員表（社員番号, 免許証番号, 氏名, 生年月日）
| キー | 意味 | 例 |
| スーパーキー | 1行を特定**できる**組なら何でも（**余計な列が入っててもいい**）（Super Key） | {社員番号, 氏名} |
| 候補キー | スーパーキーから余計な列を**削りきった**もの（**極小**）（Candidate Key） | {社員番号}、{免許証番号} |
| 主キー | 候補キーの中から**1つ選んだ代表**（重複不可・NULL不可）（Primary Key） | 社員番号 |
| 代替キー | 主キーに**選ばれなかった**候補キー（Alternate Key） | 免許証番号 |
| 外部キー | **他の表の**主キー（候補キー）を**参照する**列（Foreign Key） | 販売表の「会員番号」 |
**スーパーキー ⊃ 候補キー ⊃ 主キー**の入れ子（日本 ⊃ 大阪 ⊃ 梅田 と同じ）。候補キーから主キーを選んだ残りが代替キー。**外部キーだけ別枠**：上の4つは「自分の表の行を特定する」キー、外部キーは「**他の表とつなぐ**」キー
(
- 外部キー — 「**参照する**」
- 候補キー — 「**極小**」
+ スーパーキー — 「〜を**含む**集合」（極小じゃない）
+ 代替キー — 「**主キー以外で**一意に識別」
)
! 「代理キー（サロゲートキー）」は別物：意味のない連番などを人工的に付けた主キー
@end

@card 参照制約の削除ルール（CASCADE・RESTRICT…） | 03-1#制約と表定義
親（**注文**）を消したとき、それを**参照している子（注文明細）**をどうするかを決めるルール。親を変えたとき（更新）も同じ5つから選ぶ
| ルール | 親を消したら子は？ | 一言で |
+| CASCADE | 子も**一緒に消える** | 連鎖（道連れ） |
| RESTRICT | 子がいたら親を**消させない**（**すぐ**拒否） | 禁止 |
| NO ACTION | 子がいたら消させない（**処理の最後**に確認して拒否）。**既定** | ほぼ RESTRICT と同じ |
| SET NULL | 子の外部キーを**空（NULL）**にする | 親なし状態にする |
| SET DEFAULT | 子の外部キーを**既定値**にする | 決まった親に付け替え |
> 覚え方：**CASCADE＝滝（カスケード）**。上が崩れたら下も**連鎖して流れ落ちる**
( 見分け方
+ CASCADE — 「**自動的に削除**」「**連動して更新**」
+ RESTRICT — 「**削除を拒否**」
+ SET NULL — 「**NULLにする**」
)
| 制約 | 書き方 | 意味 |
| 主キー | PRIMARY KEY | 一意＋NOT NULL |
+| 一意性 | UNIQUE | 値の**重複を禁止**。**NULL は OK** |
| 非ナル | NOT NULL | 空値 NG |
| 参照 | REFERENCES／FOREIGN KEY | 外部キー |
| 検査 | CHECK(単価 > 0) | 条件を満たすか |
> 選択肢に出る **INTERSECT** は削除ルールでも制約でもなく SQL：2つの表の**共通部分（積集合）**を取り出す（和＝UNION、差＝EXCEPT）

@card LANの送り方（誰がいつ送るか） | 03-3#LANの送り方
| 方式 | 会議で例えると | キーワード |
| CSMA/CD | 静かなら話す。**かぶったら少し待って言い直す**（有線） | 「**衝突**を検出」「**ランダム**な時間待って再送」 |
| CSMA/CA | 静かでも**少し待ってから**話す（無線） | 「衝突を**回避**」「ACK」 |
| トークンパッシング | **輪になってマイクを回す** | 「**環状**」「**巡回**」「送信権」 |
| TDMA | **時間割**で話す順番が決まってる（時分割） | 「**タイムスロット**」 |
| 優先度制御 | **偉い順**にマイクを渡す | 「**順位付け**」 |
! **「衝突」が出たら CSMA/CD**。TDMA・優先度制御・トークンパッシングは、ぶつからないように**最初からルールで順番を決めている**ので「衝突」という言葉はそもそも出てこない（CSMA/CA は無線で衝突を**避ける**方）
(
- CSMA/CD — 有線。空いてたら送る → **衝突を検出**したら待って再送。回線の使用率30%くらいから遅延が急に増える
+ CSMA/CA — 無線。衝突は検出できないので**避ける**：空いてても少し待つ＋**ACK**で確認
+ 隠れ端末問題 — 端末同士が見えずにアクセスポイントで衝突 → **RTS/CTS**で予約
- トークンパッシング — 送信権の札（**トークン**）を持ってる人だけ送る。札は輪の上を回る。衝突なし
+ TDMA — 時分割多元接続（Time Division Multiple Access）。時間を区切って（**タイムスロット**）順番に送る
+ 優先度制御 — 優先順位の高い端末から順に送信権を渡す
)

@card VLANと認証VLAN | 03-3#LANの便利機能
**VLAN**（**V**irtual **LAN**：仮想LAN。IEEE 802.1Q）＝**1つの LAN**（1つの建物の中の、スイッチでつながってる範囲）**を、見えない壁で複数の LAN に分けたもの**
例：1台のスイッチに全員つながってるけど、設定で「幹部LAN」と「一般LAN」に分ける。**物理的には1つ、論理的には2つ**の LAN。VLAN 同士の通信には**ルータ**が要る
| 分け方 | 何で分ける？ |
| スタティック（ポートベース） | スイッチの**差込口**（席で固定） |
| アドレスベース | 端末の **MAC・IP アドレス** |
+| 認証VLAN | **ユーザー認証**（ID・パスワード、IEEE 802.1X） |
**認証VLAN**＝**席（ポート）じゃなくて「誰か（ユーザー）」でグループを決める** VLAN。PC をつないだときに**ログイン（認証）**させて、幹部なら幹部用 VLAN、一般社員なら一般用 VLAN に振り分ける
> なぜ席で分けたらダメ？：**フリーアドレス制**（毎日座る席が変わる）だと、スタティック VLAN は「3番の差込口＝幹部」と**席で固定**なので、今日その席に一般社員が座ったら**幹部用のサーバに入れてしまう**。認証 VLAN は席に関係なく**ログインした人で判定**するので、幹部がどこに座っても幹部用 VLAN になる
> オフィスで：スタティック VLAN＝「**窓際の席の人は役員会議室に入れる**」ルール（誰が座っても入れちゃう）／認証 VLAN＝「**社員証をかざした人だけ**役員会議室に入れる」ルール（座る場所は関係ない）
( 見分け方
+ 認証VLAN — 「**フリーアドレス**」「**席が変わる**」「**ユーザーごとに**」
)
( 一緒に出る（権限分けとは無関係）
- IPマスカレード（NAPT） — グローバル IP を**家族で共有**する仕組み
- IDS — 不正侵入を**見つけて通知するだけ**。アクセスを振り分ける機能はない
)
( 同じ節のスイッチの機能
+ リンクアグリゲーション（802.3ad） — 複数の回線を**束ねて1本に**。速い＋1本切れても大丈夫
+ PoE（802.3af） — **LAN ケーブルで給電**（AP やカメラの電源工事がいらない）
+ スパニングツリー（STP・802.1D） — ループ状の配線で一部ポートを止めて**ブロードキャストストーム**を防ぐ
)

@card TCPとUDP（TCP/IPとの違い） | 03-3#TCPとUDP
どっちも**4層（トランスポート層）**のプロトコル。違いは「**確実さを取るか、速さを取るか**」
| | TCP | UDP |
| 一言で | **確認しながら送る** | **送りっぱなし** |
| 接続 | 最初に**接続を確立**（3ウェイハンドシェイク）＝コネクション型 | 接続なしで**いきなり送る**＝コネクションレス |
| 届いたか確認（信頼性） | **する**（ACK）。届かなければ**再送**。ウィンドウ制御 | **しない** |
| 順番 | **並べ直して**正しい順で渡す | 保証しない |
| 速さ | 遅め | **速い**（オーバヘッドが小さい） |
| 1対多 | ×（1対1） | ○（ブロードキャスト・マルチキャスト） |
| 向いてる用途（例） | **Web・メール・ファイル転送**（HTTP・SMTP・FTP）。1文字でも欠けたら困る | **動画配信・通話・オンラインゲーム・DNS**（DHCP・SNMP・NTP も）。多少欠けても速さ優先 |
( 正式名
- TCP — Transmission Control Protocol
- UDP — User Datagram Protocol
)
> 郵便で：**TCP＝書留**（「届きました」のサインをもらう。届かなかったら**送り直す**）／**UDP＝チラシのポスティング**（**入れたら終わり**。届いたかは気にしない）
> 通話で：ビデオ通話で、一瞬途切れた所を**後から再送されても意味がない**。それより**今の声**が速く届く方が大事 → だから **UDP**
**TCP と TCP/IP は違う**：**TCP**＝4層の**プロトコル1個**の名前／**TCP/IP**＝インターネットで使う**プロトコルの全体セット**（インターネット通信の**ルール一式**）の名前（TCP/IPモデル）。代表の **TCP** と **IP** の名前を取って呼んでいるだけ。だから **UDP も TCP/IP の仲間**
| OSI | TCP/IPの4階層 | 主なプロトコル |
| 5〜7層 | アプリケーション層 | HTTP・SMTP・DNS・FTP |
+| 4層 | トランスポート層 | **TCP**・**UDP** |
| 3層 | インターネット層 | **IP**・ICMP・ARP |
| 1〜2層 | ネットワークインタフェース層 | イーサネット・Wi-Fi |
( 見分け方（問題文の言葉 → 答え）
+ TCP — 「**コネクション型**」「**再送制御**」「**信頼性**」
+ UDP — 「**コネクションレス型**」「**リアルタイム性**」「**オーバヘッドが小さい**」
)
( 同じ節に出る言葉
- ポート番号 — アプリを区別する番号。0〜1023 がウェルノウン
+ ウィンドウサイズ — ACK を待たずに送れる量
+ コネクションの識別 — 送信元IP・送信元ポート・宛先IP・宛先ポートの**4つ組**
+ プロキシ経由 — 「PC〜プロキシ」と「プロキシ〜サーバ」は**別コネクション**
+ TCPの全パケット数 — 確立3＋データ＋切断4（図で「省略」と書いてある所が問われる）
+ 伝送時間 — データ量（ビット）÷（回線速度 × 伝送効率）。**バイト→ビットの×8**、M・G の桁、効率の掛け忘れで誤答が作られる
)
補足：新しい **HTTP/3** は UDP の上の **QUIC** で動く（試験では Web＝TCP と覚えてよい）
@end

@card IPアドレスの種類 | 03-4#IPv4-アドレスの種類
**プライベートアドレスの範囲3つを覚えておけば**ほぼ解ける
| クラス | プライベートの範囲 | 覚え方 |
| A | 10.0.0.0 〜 10.255.255.255（/8） | 「**10**」で始まる |
| B | 172.16.0.0 〜 172.31.255.255（/12） | 「**172の16〜31**」 |
| C | 192.168.0.0 〜 192.168.255.255（/16） | 家のWi-Fiでよく見る「**192.168**」 |
(
- プライベート — 社内や家の中**だけ**で使う番号。ネット上では使えない
- グローバル — インターネット上で**世界に1つだけ**の番号。**この3つ以外は基本グローバル**
)

| クラス | 最初の数字 | 先頭ビット | 用途 |
| A | 0〜127 | **0** | 大規模 |
| B | 128〜191 | **10** | 中規模 |
| C | 192〜223 | **110** | 小規模 |
| D | 224〜239 | **1110** | **マルチキャスト** |
| E | 240〜255 | **1111** | 実験用 |
> 境目は **128・192・224・240**。先頭に1が1個ずつ増えるだけ：1000 0000＝128、1100 0000＝192、1110 0000＝224、1111 0000＝240
( 特殊なアドレス
+ マルチキャスト — **特定のグループ**に一斉送信。クラスD（224〜239）
- ブロードキャスト — **ネットワーク内の全員**へ。**ホスト部が全部1**（クラスCなら最後が .255）
- ネットワークアドレス — **ホスト部が全部0**。ネットワーク自体を表す番号
- ループバック — **127.0.0.1**。自分自身を指す
)
解き方（消去法なら2進数にしなくても10秒。例：208.77.188.166）
1. プライベートの範囲（10／172.16〜31／192.168）に入ってる？ → 入ってない
2. マルチキャスト（224〜239）？ → 208 なので違う
3. ブロードキャスト（最後が255）？ → 166 なので違う
4. 残りは → **グローバルアドレス**
> 今はクラスを使わず **CIDR**（Classless Inter-Domain Routing：サイダー）で「/24」のように範囲を自由に区切るのが主流。それでも試験ではクラスの知識が出る
@end

@card NATとNAPT（IPマスカレード） | 03-4#NAT・NAPT
どちらも**プライベート IP ⇔ グローバル IP** を付け替える仕組み。違いは**ポート番号まで変換するか**だけ
| 方式 | 変換するもの | グローバルIP 1個で |
| NAT | **IP アドレスだけ** | 同時に使えるのは **1台だけ** |
+| NAPT | **IP アドレス＋ポート番号** | **何台でも**同時に使える |
> マンションで：NAT＝マンションの住所が1つ → **1部屋分**しか郵便を受け取れない（部屋を区別できない）／NAPT＝住所＋**受付番号（ポート番号）**で区別 → **全部屋**が同時に受け取れる
家の Wi-Fi ルータは **NAPT**。スマホも PC も同時にネットできるのはこれのおかげ
( 名前（同じものに名前が2つ）
+ NAPT — 正式な名前（Network Address **Port** Translation）
+ IPマスカレード — Linux などでの呼び名（**masquerade＝仮面をかぶる**）。中身は NAPT と**同じ**
- NAT — Network Address Translation（アドレスだけ）
)
( 解き方
+ NAPTの穴埋め — 応答は「要求の**送信元と宛先を入れ替えたもの**」。ルータは覚えた変換を元に戻す
)
! 「IP マスカレード」と「NAPT」を**別物**として比べる選択肢は×（同じもの）
@end

## セキュリティ
@card デジタル署名の鍵（作成と検証） | 03-5#鍵の使い分け
署名を**作る**のは → **送信者の秘密鍵**、署名を**確かめる（署名の検証）**のは → **送信者の公開鍵**。問題文の「**検証**」か「**作成（生成）**」かを先に見る
> ハンコで：**秘密鍵＝本人だけが持ってる実印**（送信者がハンコを押す）／**公開鍵＝役所に登録した印鑑証明**（受信者が「本物の実印か」を照らし合わせる）
1. 送信者：メッセージを**ハッシュ値（要約）**にする
2. 送信者：それに**自分の秘密鍵**でハンコを押す → **署名**
3. 受信者：**送信者の公開鍵**で署名を開けて、中のハッシュ値を取り出す
4. 受信者：届いたメッセージから**自分でもハッシュ値を計算**
5. 2つが**一致** → **改ざんなし・本人確認 OK**
| 目的 | 使う鍵 | 誰の鍵？ |
| 暗号化（中身を隠す） | 受信者の**公開鍵**で暗号化 → 受信者の**秘密鍵**で復号 | **受信者** |
+| デジタル署名（本人証明） | 送信者の**秘密鍵**で署名 → 送信者の**公開鍵**で検証 | **送信者** |
> 覚え方：**署名は「送信者」の鍵だけ使う。押すのは秘密、確かめるのは公開**
( 見分け方
+ 署名の「**検証**」鍵 — 送信者の**公開鍵**
+ 署名の「**作成（生成）**」鍵 — 送信者の**秘密鍵**
+ 「**暗号化**」の鍵 — **受信者**の公開鍵（復号は受信者の秘密鍵）
)
! 「送信者の秘密鍵で署名を作る」は**正しい文**でも、聞かれているのが「**検証**鍵」なら答えにならない。文が正しいかより、**聞かれている方**に合っているかを見る
( 一緒に出る（証明書と改ざん検知）
+ 認証局（CA） — デジタル証明書（X.509）を**作って発行**する第三者機関。証明書は **CA の秘密鍵**で署名し、利用者は **CA の公開鍵**で検証
+ 証明書の中身 — 持ち主の名前（FQDN）・持ち主の公開鍵・有効期間・CA のデジタル署名
+ CRL — **有効期限内に**失効させた証明書の**シリアル番号**の一覧
+ OCSP — 証明書が有効かをオンラインでリアルタイム確認
+ PKI — 公開鍵を使って身元を保証する仕組み全体
+ MAC／HMAC — 共通鍵＋ハッシュで改ざん検知。共通鍵なので**否認防止はできない**（署名との違い）
+ タイムスタンプ（時刻認証） — その時刻に存在し、以降**改ざんされていない**ことの証明
)
@end

@card SSL／TLS（HTTPS） | 03-5#通信を守る
**SSL／TLS**＝通信を**暗号化**して守る仕組み。**HTTP に TLS をかぶせたのが HTTPS**
( 関係
- HTTP — Web ページを送るルール。**中身が丸見え**（**80番**）
+ TLS — 通信を**暗号化**する仕組み（Transport Layer Security）。今の標準で、TLS1.3 が最新
+ HTTPS — **HTTP ＋ TLS**。中身が暗号化されて安全（ブラウザの鍵マーク、**443番**）
- SSL — **古いバージョン**（Secure Sockets Layer）。脆弱性があって今は使われてない。名残で「SSL」と呼ぶことが多いけど、**中身は実際 TLS**
)
> 郵便で：HTTP＝**はがき**（途中で誰でも読める）／HTTPS＝**鍵付きの箱**に入れて送る（TLS が鍵の役）
| TLSの仕事 | 何を防ぐ？ | 使う技術 |
| 暗号化 | **盗聴** | 共通鍵暗号 |
| 改ざん検知 | **書き換え** | ハッシュ値（MAC） |
+| サーバ認証 | **なりすまし**（偽サイト） | **サーバ証明書**（デジタル署名） |
1. ブラウザがサーバに接続
2. サーバが**サーバ証明書**を見せる → ブラウザが **CA の公開鍵**で本物か確認
3. **公開鍵暗号**を使って、**共通鍵**を安全に決める（例：乱数をサーバの公開鍵で暗号化して送り、両方で共通鍵を作る）
4. 以降は**共通鍵**で速く暗号化して通信（＝**ハイブリッド暗号**：鍵の受け渡しだけ公開鍵）
( 見分け方
+ TLS — 「**サーバ証明書**」「**通信の暗号化**」「**HTTPS**」
)
( 一緒に出る（ほかの通信の守り・攻撃）
+ ダウングレード攻撃 — 弱い暗号を使わせる。バージョンロールバック＝古い SSL を使わせる
+ 中間者攻撃（MITM） — 通信の間に入り込んで盗聴・改ざん。証明書で相手を確かめて防ぐ
+ S/MIME — メールに署名・暗号化（ハイブリッド）
+ IPsec — **ネットワーク層**で暗号化（インターネット VPN）
+ AH／ESP／IKE — 認証・改ざん検知／＋暗号化／鍵交換（DH 法）
+ MPLS — ラベルで転送する IP-VPN の技術
)
@end

@card 無線LANのセキュリティ（プライバシーセパレータ…） | 03-5#無線LANを守る
**プライバシーセパレータ**＝同じ Wi-Fi につないでる**利用者同士が、お互いのスマホや PC にアクセスできないようにする**機能
> カフェの Wi-Fi で：みんな同じ Wi-Fi につないでるけど、**隣の席の人の PC の中を覗けない**ようにする。子機 → アクセスポイント（インターネット）は OK、子機 ↔ 子機（他人同士）は**禁止**
| 機能 | 一言で | 弱点・注意 |
| MACアドレスフィルタリング | 登録した機器**だけ**接続 OK | MAC アドレスを**偽装されたら防げない** |
| SSIDステルス | Wi-Fi の名前を**周りに見せない** | **暗号化ではない**（名前を隠すだけ） |
+| プライバシーセパレータ | **利用者同士の通信を禁止** | 公衆 Wi-Fi で使う |
( ほかの守り
+ ANY接続拒否 — SSID を空（ANY）にして探してくる端末の接続を断る
+ IEEE 802.1X — 利用者認証。RADIUS サーバ＋EAP（EAP-TLS＝クライアント証明書）
)
| 暗号化 | 中身 |
| WEP | RC4。脆弱、使っちゃダメ |
| WPA | TKIP で鍵を定期更新 |
+| WPA2 | **CCMP＝AES**。頻出 |
+| WPA3 | SAE でパスワード認証を強化 |
( 見分け方
+ プライバシーセパレータ — 「**子機同士の通信を禁止**」「**公衆Wi-Fi**」
+ MACアドレスフィルタリング — 「**登録した端末だけ**」
+ SSIDステルス — 「**SSID を隠す**」
)
> 覚え方：**Privacy（プライバシー）を Separate（分ける）**。利用者同士の間に**壁を立てる**
@end

@card 入口の守り（FW・IDS/IPS・WAF） | 03-5#入口を守る
インターネット → **FW → IDS/IPS → WAF** → Webサーバ の順。内側ほどパケットの**中身を深く見る**けど、守れる範囲は**狭く専門的**になる。3枚重ねで守る考え方＝**多層防御**（Defense in Depth）
( FW（ファイアウォール）＝門番：住所と入口番号だけ確認
- 主な層 — 3・4層
- 何を見る — **IP・ポート番号**（ヘッダだけ）
- 防げる — 許可していない**ポート・IP**からのアクセス
- 防げない — **許可したポート内**の攻撃（例：443番経由のSQLインジェクション）
)
( IDS／IPS（Intrusion Detection／Prevention System：侵入検知／侵入防止システム）＝監視カメラ／警備員
- 主な層 — 3〜7層
- 何を見る — 通信全体の**パターン・異常**
- 防げる — **ポートスキャン**・**DoS攻撃**（サービス妨害）・既知のワームや攻撃パターン
- 防げない — Webアプリ特有の細かい攻撃・**暗号化された通信**の中身
- IDS ／ IPS — 見つけて**通知するだけ** ／ 見つけて**遮断までする**（通信の経路上に置く）
)
> 覚え方：**D＝Detection（見つける）、P＝Prevention（防ぐ）**
( WAF（Web Application Firewall）＝受付：荷物の中身まで開けて確認
+ 主な層 — 7層（**HTTP/HTTPS**）
+ 何を見る — **HTTPの中身**（ペイロード）
+ 防げる — **SQLインジェクション**・**XSS**・**OSコマンドインジェクション**・**ディレクトリトラバーサル**
+ 防げない — **HTTP以外**（DNS・メールなど）
)
| 検知方式 | 仕組み | 強み・弱み |
| シグネチャ型 | 既知の攻撃パターン（シグネチャ）と照合（Signature-based） | 既知に強い。**未知は見逃す** |
| アノマリ型 | 「普段と違う」動きを検知（Anomaly-based） | **未知も見つかる**。ただし**誤検知が多い** |
(
+ フォールスポジティブ — **誤検知**：正常な通信を**攻撃と判定**してしまう（False Positive）
+ フォールスネガティブ — **検知漏れ**：攻撃を**見逃す**（False Negative）
)
( 3枚の壁で守れない攻撃（狙う相手 → 対策）
- DNSキャッシュポイズニング — DNSサーバ → **DNSSEC**（DNS Security Extensions）・ソースポートのランダム化
- メールボム（大量メール） — メールサーバ → **スパムフィルタ**
- 第三者中継 — メールサーバ（SMTP）→ SMTPサーバの設定で**中継を禁止**
)
( FW・DMZ・IDS のしくみ
- DMZ — 公開サーバ（Web・メール）を置く**緩衝地帯**。外から内部ネットワークへは直接入れない
- パケットフィルタリング — IP・ポート番号で通す/止める。**上から順に最初に合ったルール**で決まり、最後は全部拒否
+ ステートフルインスペクション — 通信の**流れ全体**の整合性を見る
+ 静的フィルタでSMTP送信 — 行き：宛先25、帰り：送信元25（相手側は1024以上）。**帰りのルールも要る**
+ WAFの置き場所 — TLSを**復号した後**・Webサーバの**前**（暗号化された中身は見えないから）
- NIDS ／ HIDS — ネットワーク全体を見るIDS ／ そのサーバを見るIDS（改ざん検知）
)
( 一緒に出る守り
+ UTM — FW・IDS/IPS・ウイルス対策などを**1台にまとめた**装置（Unified Threat Management：統合脅威管理）
+ ゼロトラスト — 社内でも信用せず、毎回検証
+ SIEM — いろんな機器の**ログを1か所に集めて相関分析**し、怪しい動きを通知
+ EDR — **端末（PC）**で侵入**後**の怪しい動きを検知して対応
+ DLP — 機密情報が**外に出るのを防ぐ**（Data Loss Prevention）
)
( 見分け方
- FW — 「**IPアドレス・ポート番号で制御**」
- IDS ／ IPS — 「不正侵入の**検知・通知**」／「**検知して遮断**」
+ WAF — 「**SQL・XSS・Webアプリ**」
+ どれでもない — 「**DNS・メール**」が対象 → 3枚の壁は関係ない（上の表の別の対策）
)
@end

@card DNSとメールを守る（DNSSEC・DKIM・SPF…） | 03-6#DNSとメールを守る
4つは「**何を守る？**（DNS かメールか）」と「**デジタル署名を使う？**」の2つで、1マスずつに決まる
| | **デジタル署名**で確かめる | **署名以外**の方法 |
| **DNS**を守る | **DNSSEC**：DNSの**応答に署名** | **ソースポートランダマイゼーション**：問い合わせの**ポート番号を毎回ランダム**にする |
| **メール**を守る | **DKIM**：**メールに署名** | **SPF**：送信元サーバの**IPアドレス**で確かめる |
1. 「**リソースレコード**」「**キャッシュサーバ**」→ **DNS** の行
2. 「**電子メール**」「**メールサーバ**」→ **メール** の行
3. 「**公開鍵・秘密鍵・署名**」→ **署名** の列（出てこなければ右の列）
( 4つをもう少し
+ DNSSEC — DNS Security Extensions。キャッシュサーバが応答の署名を**検証**して、**正しいサーバが作った**こと・**改ざんされていない**ことを確かめる（偽の応答は捨てる）
+ ソースポートランダマイゼーション — 送信元ポート番号を固定せず、**毎回ランダム**に選ぶ。偽の応答が当たりにくくなる
+ DKIM — DomainKeys Identified Mail。送信側がメールに署名し、受信側は**送信側のDNSに置いた公開鍵**で検証
+ SPF — Sender Policy Framework。送信元サーバの**IPアドレス**を、送信側の DNS の **SPFレコード**と照合
+ DMARC — SPF・DKIM が失敗したメールをどう扱うか（拒否・隔離）を送信側が宣言
)
( DNSキャッシュポイズニングの対策（全部で4つ）
+ DNSSEC — 応答の署名を検証（表の左上）
+ ソースポートランダマイゼーション — 送信元ポートをランダムに（表の右上）
+ 問合せIDのランダム化 — 問い合わせごとに 16ビットの ID を変えて、推測しにくくする
+ 外からの再帰問合せの拒否 — キャッシュサーバを**社内の利用者だけ**に使わせる
)
> なぜランダムにすると守れる？：偽の応答は、**ポート番号と問合せID の両方**を当てないと受け取ってもらえない。ポートが1つに固定なら 2¹⁶＝**65,536通り**、100個のポートから選べば 100×2¹⁶＝**約655万通り**になって、まず当たらない
! SPF・DKIM・DMARC はまとめて**送信ドメイン認証**（メールの送り主のドメインが本物か）。DNSSEC は **DNS の応答**が本物か。DKIM も SPF も **DNS を使う**けど、守っているのは**メール**
同じ節の OP25B・サブミッションポート・SMTP-AUTH・DNSBL・POP before SMTP は、次の「OP25Bとサブミッションポート」のカード
@end

@card OP25Bとサブミッションポート | 03-6#DNSとメールを守る
**セットで出る**から、流れで押さえる
**OP25B**（Outbound Port 25 Blocking）＝スパム対策で、**25番ポートで外に直接メールを送るのを禁止**する／**サブミッションポート（587番）**＝その代わりの**正規ルート**。**ID・パスワードで認証（SMTP-AUTH）**してから送らせる
1. スパマーは、**25番ポート**で外部のメールサーバに**直接**送りつける
2. 対策として、ISP が **25番ポートの外向き通信をブロック**（OP25B）
3. でもそれだと、**普通の人も外からメールを送れなくなる**
4. そこで **587番（サブミッションポート）**を用意して、**認証した人だけ**送れるようにする
> ポストで：25番＝**誰でも使える無人ポスト**（迷惑な手紙をばらまかれる）／OP25B＝無人ポストを**封鎖**／587番＝**受付窓口**。**身分証（ID・パスワード）を見せた人だけ**手紙を出せる
| ポート | 用途 |
| 25 | SMTP（**サーバ同士**のメール転送） |
+| 587 | **サブミッションポート**（利用者 → メールサーバ、**認証あり**） |
| 110 | POP3（受信。端末に落とす） |
| 143 | IMAP（受信。サーバに置いたまま） |
( 見分け方
+ サブミッションポート — 目的は「**SMTP-AUTH による送信者認証**」
+ OP25B — 「**25番への直接送信を止める**」「スパム対策」
)
( 一緒に出る（メールの送り主を確かめる）
+ SMTP-AUTH — SMTP に利用者認証（ID・パスワード）を追加
+ SPF — 送信元の **IP アドレス**を DNS の SPF レコードと照合
+ DKIM — メールの**デジタル署名**を、DNS に置いた公開鍵で検証
+ DMARC — SPF・DKIM が失敗したメールをどう扱うか（拒否・隔離）を送信側が宣言
+ DNSBL — 迷惑メール送信元 IP のブラックリスト
+ POP before SMTP — 受信の認証が通ったら一定時間だけ送信 OK
)
@end

@card ボットとC&Cサーバ | 03-6#攻撃の手口
**C&Cサーバ**（Command and Control：指令・制御サーバ）＝乗っ取った PC たちに「**一斉に攻撃しろ**」と命令を出す**司令塔**
| 用語 | 一言で | 例えると |
| ボット | マルウェアに感染して**乗っ取られた PC** | **操り人形** |
| ボットネット | ボットの**集団** | **操り人形の軍団** |
+| C&Cサーバ | ボットに**指令を出す**サーバ | **人形使いの司令室** |
| コネクトバック通信 | ボットの方から C&C サーバに「**次の命令ある？**」と問い合わせる | 人形が**自分から電話をかけて**指示を聞く |
> なぜコネクトバック通信？：外から社内の PC に通信しようとしても、**ファイアウォールで止められる**。でも**社内から外への通信**（Web を見るのと同じ）は通りやすい。だから**感染 PC 側から定期的に問い合わせる**形にしている
1. 攻撃者が C&C サーバに命令をセット
2. 感染 PC（ボット）が**定期的に C&C サーバへ問い合わせ**（コネクトバック）
3. 命令を受け取って、**一斉に DDoS 攻撃**や情報の盗み出しをする
( 見分け方
+ C&Cサーバ — 「**ボットに指令**」「**遠隔操作**」「**ボットネットを制御**」
)
( 一緒に出る（サービスを止める）
+ DDoS — 大量のボットから一斉に DoS 攻撃
+ SYN Flood — SYN を大量に送って待ち状態で埋める
+ Smurf — 送信元を標的に偽装した ICMP をブロードキャスト
+ DNSリフレクタ（DNS amp） — 送信元を標的に偽装して DNS に問い合わせ → 増幅した応答を標的へ。NTP 増幅も同じ形
)
@end

@card サイドチャネル攻撃と暗号解読 | 03-6#攻撃の手口
**サイドチャネル攻撃**（Side Channel Attack）＝暗号を**正面から解くんじゃなくて**、機械が動くときに漏れる**電力・時間・電磁波**などの「**横から漏れる情報**」から鍵を盗む攻撃
> 金庫破りで：番号を**全部試す**＝ブルートフォース攻撃（正面から）／ダイヤルを回したときの**カチッという音や手応え**で番号を当てる＝サイドチャネル攻撃（横から）
| 種類 | 何を見る？ |
| タイミング攻撃 | 処理にかかる**時間**の差 |
| 電力解析攻撃 | **消費電力**の変化 |
| 電磁波解析攻撃 | 機器から漏れる**電磁波**（**テンペスト攻撃**） |
| 故障利用攻撃 | わざと**故障**させて、計算ミスから推測 |
( 暗号解読の方法（計算・数学で解く方）
+ 差分解読法 — 2つの平文の**差**と暗号文の差を比べる
+ 線形解読法 — 暗号を**線形の式で近似**する
- ブルートフォース攻撃 — 鍵を**全部試す**（総当たり攻撃）
)
! 「**電力**」「**時間**」「**電磁波**」「**故障**」など**物理的な情報**が出たらサイドチャネル。差分・線形・総当たりは全部**計算**で解く方法
@end

@card 似た名前の「コード」 | 03-6#攻撃の手口
家の防犯に例えると
| 名前 | 一言で | 例え |
| エクスプロイトコード | **脆弱性を突く**攻撃用コード | 壊れた鍵を開ける**合鍵** |
| MAC | **改ざんを見つける**ためのコード（Message Authentication Code：メッセージ認証符号） | 封筒の**封印シール** |
| シグネチャコード | マルウェアを**見分ける**ための特徴（定義ファイル） | **指名手配の顔写真** |
| ワンタイムパスワード | **毎回変わる**認証コード | **使い捨ての合言葉** |
> MAC（HMAC）は**共通鍵＋ハッシュ**で改ざんを検知する。共通鍵なので**否認防止はできない**（デジタル署名との違い）。ワンタイムパスワードは時刻同期方式（トークンに毎回変わる数字）やチャレンジレスポンスで作る
> エクスプロイトコードは**攻撃にも、守る側の検証**（脆弱性が本当にあるかの確認）**にも使える**。合鍵と同じで、泥棒が使えば悪用、鍵屋が使えば点検。**Exploit＝悪用する・つけ込む**
( 見分け方
+ エクスプロイトコード — 「脆弱性を**悪用**」「**攻撃コード**」
+ MAC — 「**改ざん検知**」「シークレットデータ＋**ハッシュ**」
+ シグネチャ — 「マルウェアの**特徴**」「**定義ファイル**」
+ ワンタイムパスワード — 「ログインの**たびに変化**」
)
@end

@card デジタルフォレンジックス（IT版の鑑識）と EDR・DLP・SIEM | 03-6#見張る・調べる
**デジタルフォレンジックス**（Digital Forensics）＝事件が起きた**後**に、PC やサーバに残った**証拠（ログ・削除データなど）を集めて分析**し、**裁判でも使える形**で残すこと。**IT版の鑑識**
1. **収集**：現場の指紋や髪の毛を**集める**＝データを**改ざんせずに**コピー
2. **検査**：集めた物から**関係ありそうなものを抜き出す**
3. **分析**：「犯人はいつ・どこから入った？」を**突き止める**
4. **報告**：結果をまとめて**報告書**にする
| 道具 | 一言で | いつ |
+| デジタルフォレンジックス | 削除されたログも復元して**痕跡を調べる** | 事件の**後** |
| EDR | PC（**端末**）上でマルウェアを**検知・対応** | 事件の**最中** |
| DLP | 機密情報が**外に出るのを防ぐ** | 事件の**前** |
| SIEM | ログを集めて**リアルタイムに分析** | 事件の**最中** |
( 正式名
- EDR — Endpoint Detection and Response（端末での検知と対応）
- DLP — Data Loss Prevention（情報漏えい防止）
- SIEM — Security Information and Event Management（シーム）
)
> 覚え方：**Forensics＝法医学・鑑識**。事件の**後に証拠を調べる**
( 見分け方（問題文の言葉 → 答え）
+ デジタルフォレンジックス — 「**痕跡**」「**証拠**」「**削除データの復元**」「**法的紛争**」
- EDR — 「**端末で検知・対応**」
- DLP — 「**情報漏えい防止**」
- SIEM — 「**ログ集約**」「**相関分析**」
)
( 同じ節に出る言葉（おとり・隔離・わざと壊して調べる）
+ サンドボックス — 隔離した場所で動かして様子を見る
+ ハニーポット — わざと侵入しやすくした**おとり**で攻撃を観察
+ 検疫ネットワーク — つなぐ前に端末を検査し、問題があれば隔離
+ ファジング — 変なデータを大量に入れて脆弱性を探す
+ ダークネット — 使われてないIP空間。届く通信は怪しい
)
@end

@card セキュアブート（起動を守る） | 03-6#起動を守る
PCが起動する流れ（電源ON → 使える状態）
1. **ファームウェア**（BIOS／UEFI）が動く：マザーボードに入っている**最初のプログラム**
2. **ブートローダ**を読み込む：OSを呼び出す**案内係**
3. **OS**（Windows・macOS など）が起動
4. **ドライバ**・アプリが動く
**セキュアブート**＝2〜3の段階で、読み込むプログラムに**デジタル署名（本物のハンコ）があるかチェック**して、**偽物なら起動しない**仕組み
> なぜ必要？：**ブートキット**（OSより先に動くマルウェア）は、OSが起動する**前**に入り込む。OSが立ち上がってからのウイルス対策ソフトでは**手遅れ** → **起動の段階でチェック**する
> 空港で：セキュアブート＝**搭乗前のパスポートチェック**（本物の印がない人は搭乗させない）／ウイルス対策ソフト＝**飛行中の警備**（もう乗った後）
( 用語
- BIOS — Basic Input/Output System。昔の起動用ファームウェア
+ UEFI — Unified Extensible Firmware Interface。BIOSの**後継**。セキュアブートは **UEFIの機能**
+ ブートローダ — OSを呼び出す案内係
+ TPM — Trusted Platform Module。PCに載っている**鍵の金庫チップ**。起動時の状態を記録・検証。Windows 11 の必須条件
)
| 名前 | やり方 | 何を確かめる？ |
| BIOSパスワード | 起動時に BIOS のパスワードを入力 | **人**（パスワード） |
| HDDパスワード | 起動時に HDD/SSD のパスワードを入力 | **人**（パスワード） |
| **セキュアブート** | 起動時に**デジタル署名を検証**して、正しいものだけ実行 | **プログラム**（署名） |
| ウイルス対策ソフト | OS 起動**後**にスキャン | （タイミングが遅い） |
( 見分け方
+ セキュアブート — 「**デジタル署名を検証**」「**OS起動前**」
)
! BIOS・HDDパスワードは**人をパスワードで**確認、セキュアブートは**プログラムを署名で**確認
@end

@card TPMと似た略語（SIEM・UTM・SPF） | 03-6#起動を守る
4つとも**キーワード1語**で見分けられる
| 名前 | 一言で | 例えると |
+| TPM | PC に載っている**セキュリティ専用チップ**。**鍵の生成・保管**、暗号処理 | PC の中の**金庫** |
| SIEM | いろんな機器の**ログを1か所に集めて分析**し、怪しい動きを通知 | 全部の防犯カメラ映像を集める**監視センター** |
| UTM | FW・IDS/IPS・ウイルス対策などを**1台にまとめた**装置 | **警備の全部入りセット** |
| SPF | メールの送信元を **IPアドレス**で確認 | 差出人の**住所チェック** |
( 正式名
+ TPM — **T**rusted Platform Module
- SIEM — Security Information and Event Management（シーム）
- UTM — **U**nified Threat Management（統合脅威管理）
- SPF — Sender Policy Framework
)
( TPMをもう少し
+* ハードウェア（チップ） — ソフトじゃないから**鍵を盗み出されにくい**（**耐タンパ性**＝中身を解析・改ざんされにくい度合い）
+ TPMの使い道 — **ストレージ暗号化**（Windows の **BitLocker**）、**起動時の改ざんチェック**（起動の状態を記録。**セキュアブート**と組んで使う）
+ Windows 11 — TPM（2.0）が**必須条件**になった
)
> 覚え方：**TPM＝T**rusted（信頼できる）**チップ**／**SIEM＝ログの「集」中管理**／**UTM＝U**nified（全部入り）
( 見分け方（問題文の言葉 → 答え）
+ TPM — 「**チップ**」「**鍵生成**・ハッシュ演算・**暗号処理**を行うセキュリティチップ」
- SIEM — 「ログを**一元管理**」「**相関分析**」
- UTM — 「複数のセキュリティ機能を**統合**」
- SPF — 「**送信ドメイン認証**」
)
@end

@card セキュアOS（最小特権・強制アクセス制御） | 03-6#OSを守る
**セキュアOS**＝**管理者（root）が乗っ取られても被害を小さくできる**ように、①**最小特権** ②**強制アクセス制御（MAC）** の2つの機能を入れたOS。代表例は **SELinux**（Linux 用のセキュアOS機能）
( 2つの機能
+* 最小特権 — 管理者に**全部の権限をまとめて渡さず**、必要な操作の分だけ**小分け**にして渡す → 1つのアカウントが乗っ取られても**できることが限られる**
+* 強制アクセス制御（MAC：Mandatory Access Control） — **システム全体のルール（セキュリティポリシー）**でアクセスを決め、**管理者でもそのルールを変えられない**
- 任意アクセス制御（DAC：Discretionary Access Control） — 普通のOS。**ファイルの持ち主**が権限を自由に決める
)
| | 普通のOS | セキュアOS |
| 決めるのは | **ファイルの持ち主**が自由に設定（任意アクセス制御：**DAC**） | **システム全体のポリシー**で強制（強制アクセス制御：**MAC**） |
| rootは | **何でもできる** | ポリシーに**逆らえない** |
+| 乗っ取られたら | **全部やられる** | ポリシーで禁止されたことは**できない** → **改ざんを防げる** |
> 会社で：普通のOS＝**社長の鍵（マスターキー）1本で全部の部屋が開く** → 盗まれたら終わり／セキュアOS＝**部屋ごとに鍵が分かれていて**、しかも**ビルのルールで社長でも入れない部屋がある**
( 見分け方（問題文の言葉 → 答え）
+ セキュアOS — 「**強制アクセス制御**」「**最小特権**」「侵入されても**改ざんを防ぐ**」
- 多要素認証 — 「パスワード＋**トークン**」
- WAF — 「**Webアプリへの攻撃**をブロック」
- SSO（シングルサインオン） — 「**1回のログイン**で複数システム」
)
! 「**MAC**」は3つある：**強制アクセス制御**（Mandatory Access Control）／**MACアドレス**（Media Access Control）／**メッセージ認証符号**（Message Authentication Code）。文脈で見分ける
@end

@card CSIRTの6種類 | 03-6#攻撃の段取りと社会の仕組み
CSIRT には**6種類**あって、違いは「**誰のために動くか（サービス対象）**」だけ
( 種類 — 誰のために → 何をする（例）
+ 組織内CSIRT — **自分の会社**のため → 社内の事件に対応（ふつう「CSIRT」と言えばこれ）
+ 国際連携CSIRT — **国**のため → 国の代表として**海外と連絡**（JPCERT/CC）
+ コーディネーションセンター — **他のCSIRT**のため → CSIRT同士の**情報連携・調整役**（グループ企業のCSIRTをまとめる）
+ 分析センター — 世の中・利用者のため → 攻撃の**傾向分析**・マルウェア解析・**注意喚起**（セキュリティ研究機関）
+ ベンダーチーム（PSIRT） — **自社製品の利用者**のため → 製品の脆弱性を直して**パッチを出す**（メーカーのPSIRT）
+ インシデントレスポンスプロバイダ — **お客さん（有償）**のため → CSIRTの仕事を**お金をもらって代行**（セキュリティ会社・SOC事業者）
)
> 消防で：組織内＝**会社の自衛消防隊**／国際連携＝**国の消防庁**（海外とも連絡）／コーディネーション＝**消防の指令センター**（各隊を調整）／分析センター＝**火災の原因を研究する機関**／PSIRT＝**ストーブのメーカー**（リコール対応）／インシデントレスポンスプロバイダ＝**民間の警備会社**（有料で請け負う）
( まわりの言葉
+ CSIRT — インシデント（事件）対応チーム
+ SOC — 24時間監視して攻撃を**検知・分析**する組織（**対応する**のは CSIRT）
+ トリアージ — 対応の**優先順位付け**（インシデントハンドリングの1つ）
+ J-CRAT — 標的型攻撃のレスキュー隊（IPA）
)
( 見分け方
+ コーディネーションセンター — 「**他のCSIRT**」「**連携・調整**」
+ 国際連携CSIRT — 「**国を代表**」
+ PSIRT — 「**自社製品**」
+ インシデントレスポンスプロバイダ — 「**有償で請け負う**」
+ 分析センター — 「**傾向分析・注意喚起**」
)
@end

@card ISMAPと似た制度 | 03-6#攻撃の段取りと社会の仕組み
**ISMAP**（イスマップ：政府情報システムのためのセキュリティ評価制度）＝**国が「このクラウドなら安全」とお墨付きを与えて、リストに載せる制度**。政府機関は、基本的に**このリストの中からクラウドを選ぶ**
> 例えると：国の「**安全なクラウドの指定業者リスト**」。AWS・Google Cloud・Microsoft Azure などが登録されている
> なぜできた？：国が「**クラウド・バイ・デフォルト原則**」（システムを作るときは**まずクラウドを検討しろ**）を決めた。でも各省庁がバラバラにクラウドの安全性を調べるのは大変 → **国がまとめて事前審査**することにした
| 名前 | 何を認定する？ |
| プライバシーマーク | **個人情報**をちゃんと扱える**会社**（JIS Q 15001） |
+| ISMAP | 政府が使える**クラウドサービス**を事前に評価・登録 |
| ISMSクラウドセキュリティ認証 | クラウド向けの**セキュリティ管理体制**（ISO/IEC 27017） |
| ISMS適合性評価制度 | 会社の**情報セキュリティ管理**の仕組み（JIS Q 27001） |
| 越境移転のルール | 個人データを**海外に渡すとき**のルール（個人情報保護法。原則本人の同意） |
( 見分け方
+ ISMAP — 「**政府**」「**クラウドサービス**」「**事前に評価・登録**」
+ プライバシーマーク — 「**個人情報**」「**事業者（会社）を認定**」
)
> 覚え方：**ISMAP＝I**nformation system **S**ecurity **M**anagement and **A**ssessment **P**rogram。「**政府のクラウド選びの名簿**」
( 同じ節に出る言葉
+ CRYPTREC — 電子政府推奨暗号リスト（国が「この暗号なら安全」と出す名簿。推奨・推奨候補・運用監視）
+ 早期警戒パートナーシップ — 脆弱性情報は IPA が受付・JPCERT/CC が調整・JVN で公表
+ セキュリティバイデザイン — 企画・設計の段階からセキュリティを組み込む
)
@end

@card 脆弱性の名札（CVE・CWE・CVSS…） | 03-6#脆弱性の名札
脆弱性情報を**世界共通のルールで管理するための「名札」セット**。頭は全部 **C＝Common（共通）**なので、**2文字目以降の英単語**で区別する
| 略称 | 正式名称・日本語 | 何に名札をつける？ |
| CVE | Common **Vulnerabilities** and Exposures（共通脆弱性識別子） | **個別の脆弱性**1つ1つ |
| CWE | Common **Weakness** Enumeration（共通脆弱性タイプ一覧） | 脆弱性の**種類**（タイプ） |
| CCE | Common **Configuration** Enumeration（共通セキュリティ設定一覧） | セキュリティの**設定項目** |
| CPE | Common **Platform** Enumeration（共通プラットフォーム一覧） | **製品**（OS・アプリ・機器） |
| CVSS | Common Vulnerability **Scoring** System（共通脆弱性評価システム） | 脆弱性の**深刻度を点数化**（0.0〜10.0） |
> 英単語の意味で覚える：**V**ulnerability＝脆弱性 → 個別の脆弱性、**W**eakness＝弱点 → 弱点の種類、**C**onfiguration＝設定、**P**latform＝土台 → 製品、**S**coring＝採点 → 点数
( Log4j の脆弱性で全部つなげると
+ CPE — どの製品？ → Apache Log4j
+ CVE — どの脆弱性？ → CVE-2021-44228（**個別の番号**）
+ CWE — どんな種類の弱点？ → **タイプごとの番号**（SQLインジェクションなら CWE-89）
+ CVSS — どれくらいヤバい？ → 10.0（最高）
)
( 脆弱性情報の流れ（日本）
+ 早期警戒パートナーシップ — 脆弱性情報は **IPA が受付・JPCERT/CC が調整・JVN で公表**
+ JVN — 日本の脆弱性情報サイト。CVE で引くと **CVSS の点数や CWE の種類**も一緒に載っている
)
! **CVE＝事件ごと**の番号（この製品のこのバグ）、**CWE＝手口の種類**の番号（SQLインジェクションなど）。ここが一番のひっかけ
> **SCAP**（セキュリティ設定共通化手順）＝ CVE・CCE・CPE・CVSS と検査用の言語（XCCDF・OVAL）をまとめて点検を自動化する仕組み。たまに選択肢に出る。**CWE は SCAP に入っていない**
@end

## 開発・マネジメント
@card UMLの図（14種類） | 04-1#UML
UMLの図は**14種類**。大きく2つ：**構造図**＝システムが**何でできてるか**（静的）、**振る舞い図**＝システムが**どう動くか**（動的）。よく出るのは★の7つ。「**ネットショップ**」で例える
| 構造図 | 一言で | ネットショップで |
| ★クラス図 | クラスの**属性・操作・関係** | 「会員」「商品」「注文」の項目と、つながり（1人の会員が複数注文） |
| オブジェクト図 | クラス図の**具体例**（ある瞬間のデータ） | 「会員：田中」「注文：No.001」 |
| ★コンポーネント図 | ソフトの**部品**と依存関係 | 決済部品・在庫部品・画面部品 |
| ★配置図 | ソフトが**どのマシンに置かれるか** | Webサーバ・DBサーバに何を置くか |
| パッケージ図 | クラスを**フォルダ分け** | 「会員系」「注文系」パッケージ |
| 複合構造図 | クラスの**内部構造** | （ほぼ出ない） |

| 振る舞い図 | 一言で | ネットショップで |
| ★ユースケース図 | **誰が・何をできるか**（人型＋楕円） | 客：「商品を探す」「購入する」、店長：「商品を登録する」 |
| ★アクティビティ図 | 処理の**流れ**（フローチャート風） | カートに入れる → 支払う → 在庫あり？ → 発送 |
| ★ステートマシン図 | 1つの物の**状態の移り変わり**（状態遷移図） | 注文：受付中 → 支払済 → 発送済 → 配達完了 |
| ★シーケンス図 | オブジェクト間のやりとりを**時間順**に（縦線＋矢印） | 客 → 画面 → 注文処理 → 在庫DB の順にメッセージ |
| コミュニケーション図 | やりとりを**つながり重視**で（番号付き矢印） | シーケンス図と同じ内容を関係図っぽく描く |
| タイミング図 | **時間軸での状態変化** | （ほぼ出ない） |
| 相互作用概要図 | アクティビティ図＋シーケンス図 | （ほぼ出ない） |
( 似てるペアの見分け方（ここが狙われる）
+ シーケンス図 ／ コミュニケーション図 — 同じやりとりを、**時間順**で描くか、**つながり**で描くか
+ アクティビティ図 ／ ステートマシン図 — **処理の流れ**か、**1つの物の状態**の変化か
- クラス図 ／ オブジェクト図 — **設計図（型）**か、**具体的なデータ**か
+ コンポーネント図 ／ 配置図 — **ソフトの部品**か、**ハード（マシン）への配置**か
)
( キーワードで1発判定
- ユースケース図 — 「**アクター**」「**利用者の視点**」
+ シーケンス図 — 「**時系列**」「**メッセージの順序**」
+ ステートマシン図 — 「**状態**」「**遷移**」「**イベント**」
+ アクティビティ図 — 「**処理の流れ**」「**分岐・並行処理**」
- クラス図 — 「**属性・操作**」「**多重度**（1対多など）」
+ 配置図 — 「**ノード**」「**物理的な配置**」
)
( クラス図の記号
+ △（白三角） — 汎化（親の側に付ける）
+ ◇（白ひし形） — 集約（全体の側）。部品は全体が消えても残る
+ ◆（黒ひし形） — コンポジション。全体が消えたら部品も消える
+ 多重度 — 1・0..1・0..*・1..*。**相手1つから見た自分の数を、自分の側の端に**書く（社員—年：社員側「0..*」、年側「1」）
)
@end

@card モジュール結合度と強度 | 04-1#結合度と強度
**結合度**（Coupling）＝モジュール**同士**のつながり → **弱いほど良い**。**強度**（Cohesion・凝集度）＝モジュール**内部**のまとまり → **強いほど良い**。合言葉は「**疎結合・高凝集**」（外とはゆるく、中はしっかり）
| 結合度（良い順） | 何を共有・受け渡しする？ |
| ① データ結合 | 引数で**単一のデータ**（Data Coupling） |
| ② スタンプ結合 | 引数で**構造体**（レコード）（Stamp） |
| ③ 制御結合 | 引数で**動作を指示**（フラグなど）（Control） |
| ④ 外部結合 | **グローバル変数**（単一）（External） |
| ⑤ 共通結合 | **グローバルな構造体**（Common） |
| ⑥ 内容結合 | 相手の**内部を直接**いじる（Content） |
> 語呂「**です、背が今日ない**」＝**デ**ータ→**ス**タンプ→**セ**イギョ→**ガ**イブ→**キョウ**ツウ→**ナイ**ヨウ。3グループで見る：引数で渡す（①〜③）／グローバルで共有（④⑤）／中身を直接いじる（⑥）。「**単一 → 構造体**」の順に悪くなるパターンが2回出てくる
| 強度（良い順） | まとめた理由 |
| ① 機能的強度 | **1つの機能**だけ（Functional） |
| ② 情報的強度 | **同じデータ**を扱う機能を集めた（入口は別々）（Informational） |
| ③ 連絡的強度 | 同じデータを使って**順番に**処理（Communicational） |
| ④ 手順的強度 | 決まった**手順の順**に並べた（Procedural） |
| ⑤ 時間的強度 | **同じタイミング**で動く（例：初期化処理）（Temporal） |
| ⑥ 論理的強度 | **似た処理**をまとめて、フラグで切り替え（Logical） |
| ⑦ 暗合的強度 | **たまたま**寄せ集めただけ（Coincidental） |
> 語呂「**気丈に連れて、持論案**」＝**キ**ノウ→**ジョウ**ホウ→**レン**ラク→**テ**ジュン→**ジ**カン→**ロン**リ→**アン**ゴウ。**まとめた理由がちゃんとしてるほど強い**：1機能 → 同じデータ → 手順 → 時間 → 似てるだけ → 偶然
( 見分け方（問題文の言葉）
- データ・スタンプ・制御 — 「**引数**」→ 中身が単一か、構造体か、指示か
- 外部・共通 — 「**大域・グローバル**」→ 単一なら外部、構造体なら共通
- 内容 — 「**内部を直接参照**」「**JUMP**」
)
! 「引数」だけ見てデータ結合系と決めない。引数で**動作を指示**していたら**制御結合**
@end

@card 保守の4種類 | 04-2#再利用と保守
まず「**問題を直す（訂正）**」か「**良くする（改良）**」かで2つに分かれる
| 分類 | 種類 | いつ・何を | 車で |
| **訂正** | **是正保守** | **起きた問題**を直す | **故障したから**修理 |
| 〃 | **予防保守** | **まだ起きてない問題**を先に直す | 壊れる前に**部品交換** |
| **改良** | **適応保守** | **環境の変化**に合わせる | **法律が変わって**装備を追加 |
| 〃 | **完全化保守** | 問題はないけど**もっと良くする** | 燃費アップ・ナビ追加・**取扱説明書を直す** |
( 見分け方
- 是正 — 「**発見された問題を直す**」
+ 予防 — 「**潜在的な障害を事前に**」（JIS：**運用障害になる前**）
+ 適応 — 「**環境の変化**」（OS・法律・新しい機器）
+ 完全化 — 「**性能向上・機能追加・文書の改善**」（JIS：**故障として現れる前**）
)
> 覚え方：**問題あり → 是正、問題になりそう → 予防、外が変わった → 適応、全部OKだけど磨く → 完全化**
! 「ソースコードに**仕様書を合わせる**」＝文書の改善 → **完全化保守**（バグも環境の変化もない）
@end

@card クラッシングとファストトラッキング | 05-1#スケジュール
どちらも**クリティカルパスを縮めて**、完了予定日に間に合わせる手法
@fig crash | クラッシングとファストトラッキング | 計画13日・完了予定日は11日目。クラッシングは10日、ファストトラッキングは11日で終わる
| | クラッシング | ファストトラッキング |
| やり方 | クリティカルパス上の作業に**資源を追加投入**して、1つ1つを短くする | 順番に行う予定だった作業を**並行**して行う |
| 例 | メンバーの**時間外勤務**を増やす・業務に**詳しいメンバーを増員**する | 全体の設計が終わる**前に**、仕様が固まったモジュールの開発を始める |
| 代償 | **お金がかかる** | **手戻りのリスク** |
( 縮め方のルール
- クリティカルパス — 一番長い経路＝全体の日数を決める。ここが1日遅れたら全体も遅れる
+ 縮める作業 — **クリティカルパス上**で、1日縮める費用（費用増加率）が**一番安い**ものから1日ずつ
+ 縮めたら — クリティカルパスが変わっていないか**確認し直す**
)
> 見分け方：「**資源の追加・増員・残業・費用**」→ クラッシング、「**並行・前倒し・重ねる**」→ ファストトラッキング
@end

@card 監査は「促す」まで（内部統制の役割分担） | 05-2#内部統制
監査する人は「**改善を促す（勧める）のはOK、自分で直すのはNG**」。「促す」＝「**ここを直した方がいいですよ**」と言うところまで。実際に直す**責任と権限は経営者側**にある
| 監査人の仕事 | OK？ |
| 調べる（検討・評価） | ○ |
| 報告する | ○ |
+| **改善を勧める**（改善勧告・助言）＝「促す」 | ○ |
| 改善後に**ちゃんと直ったか確認**（フォローアップ） | ○ |
+| **自分で直す・実行する** | **×** |
> なぜ自分で直したらダメ？：自分で直したものを、次の監査で自分がチェックすることになる → **自分の宿題を自分で採点**する状態になって、**独立性**が失われる
> 健康診断で：医者（監査人）は検査して「**血圧が高いから塩分を控えてね**」と助言する（○）。実際に食生活を変えるのは**本人（経営者）**。医者が本人の代わりにご飯を作るのは役割外（×）
| 人 | 本当の役割 |
+| 経営者 | 内部統制を**整備・運用**する（**最終責任**者） |
| 取締役会 | 内部統制の**基本方針を決める**（経営者を監督する） |
| 監査役 | 取締役の仕事の監査の一環で、**独立した立場**から内部統制を**監視・検証** |
+| 内部監査人 | **モニタリング**の一環として内部統制を**検討・評価**し、**改善を促す** |
| 株主 | 内部統制の責任は**ない** |
( 見分け方（問題文の言葉 → 答え）
+ 経営者 — 「**最終的な責任**」
- 取締役会 — 「**基本方針を決定**」
- 監査役 — 「**独立した立場で監視**・検証」
+ 内部監査人 — 「**検討・評価**」「**改善を促す**」
)
! 役割を**入れ替えた**選択肢が定番。動詞で当てる：**決める**＝取締役会／**整備・運用**＝経営者／**監視・検証**＝監査役／**促す**＝内部監査人
> 内部監査人の「**モニタリング**」は、内部統制の**6つの基本的要素**の1つ（統制環境・リスクの評価と対応・統制活動・情報と伝達・**モニタリング**・ITへの対応）
@end

@card EAの参照モデル | 06-1#EA
4つの体系 → 5つの参照モデル
| 体系 | 参照モデル | キーワード |
| BA | **BRM**（Business Reference Model：政策・業務参照モデル） | **業務**の分類 |
| 〃 | **PRM**（Performance Reference Model：業績測定参照モデル） | **KPI**・投資効果 |
| DA | **DRM**（Data Reference Model：データ参照モデル） | データの**名称・定義・属性** |
| AA | **SRM**（Service Component Reference Model：サービスコンポーネント参照モデル） | 機能の**部品化・再利用** |
| TA | **TRM**（Technical Reference Model：技術参照モデル） | **技術**の標準化（土台） |
( 4つの体系（上ほど抽象的＝仕事、下ほど具体的＝機械）
- BA — 政策・業務体系（Business Architecture）：**業務の流れ** → DFD・業務流れ図（WFA）
- DA — データ体系（Data Architecture）：**データの構造** → E-R図
- AA — 適用処理体系（Application Architecture）：**システムの機能構成**
- TA — 技術体系（Technology Architecture）：**ハード・ネットワーク**
)
> 頭文字は英語そのまま：**B**usiness＝業務・**P**erformance＝業績・**D**ata＝データ・**S**ervice Component＝部品・**T**echnical＝技術
! 部品**そのもの**の分類 → **SRM**、部品を**動かす土台**（プラットフォーム・技術） → **TRM**
@end

@card BPR・BPM・BPO・RPA（業務を直す＝部屋の掃除） | 06-1#業務を直す
6つとも「**部屋の掃除**」に例えると一気に覚えられる
( 掃除で覚える
-* BPR — **大掃除**。家具ごと捨てて**部屋をゼロから作り直す**＝業務を**抜本的に**再設計（一回きり）
-* BPM — **毎日の掃除**。ちょっとずつ**ずっと回す**＝業務を**継続的に**改善（PDCA）
- BPO — 掃除を**業者に丸投げ**＝業務ごと外部に委託（海外の業者なら**オフショア**）
- RPA — **ルンバ**。決まった作業を**機械が代わりにやる**。部屋の配置（業務の手順）は**そのまま**
+ ECRS — **片付けの順番**（下の表）
+ BPMN — 掃除の**手順書を、誰が読んでも分かる共通の書き方**で描くルール＝業務の流れを統一の記法で描く
)
| ECRS | 改善の順番 | 掃除で |
| E | **排除**（Eliminate）：やめられないか | まず**捨てる**（いらん物はないか） |
| C | **結合**（Combine）：まとめられないか | **まとめる**（同じ物は1か所に） |
| R | **交換**（Rearrange）：入れ替えられないか | **並べ替える**（使う順に置き直す） |
| S | **簡素化**（Simplify）：簡単にできないか | **楽にする**（収納グッズで簡単に） |
( 正式名
- BPR — Business Process **Re**engineering（作り直す）
- BPM — Business Process **Management**（管理し続ける）
- BPO — Business Process **Outsourcing**（外に出す）
- RPA — **Robotic** Process Automation（ロボットで自動化）
- BPMN — Business Process Model and **Notation**（表記法）
)
> 覚え方：**BPR＝大掃除／BPM＝毎日の掃除／BPO＝業者／RPA＝ルンバ**
( 見分け方（問題文の言葉 → 答え）
- BPR — 「**抜本的**」「**根本的に再設計**」→ **大掃除**
- BPM — 「**継続的**」「**PDCA**」→ **毎日の掃除**
- RPA — 「**ソフトウェアロボット**」「業務は**そのまま**自動化」→ **ルンバ**
- BPO — 「業務**プロセスごと外部**に委託」→ **業者に丸投げ**
)
@end

@card クラウドの種類（IaaS・PaaS・SaaS） | 06-1#借りる
どれが「すごい」とかじゃなくて、**任せる量が違うだけ**。業者に任せるほど**ラク**、でも**自由度は下がる**／自分でやるほど**大変**、でも**好きにカスタムできる**
| 種類 | 業者がやること | 自分でやること |
| オンプレミス | なし | **全部** |
| IaaS | 建物（サーバ・ネットワーク） | OS・ミドルウェア・アプリ |
+| PaaS | 建物＋設備（ミドルウェアまで） | **アプリだけ** |
| SaaS | **全部** | **使うだけ** |
> 住まいで：オンプレミス＝**土地を買って家を建てる**／IaaS＝**空っぽの部屋を借りる**（家具・家電は自分で）／PaaS＝**家具付き**の部屋を借りる／SaaS＝**ホテル**に泊まる
( どれを選ぶ？（例）
+ IaaS — **自由に作りたい・細かく設定したい**（AWS EC2）
+ PaaS — **アプリ開発に集中したい**（Heroku・Vercel）
+ SaaS — **作らずにすぐ使いたい**（Gmail・Slack・Notion）
)
身近な例：Notion・Slack＝**SaaS**、Web アプリを載せる Vercel＝**PaaS**
! 「バッチ処理の**ジョブ監視**」のような**自分のアプリの面倒を見る作業**は、IaaS でも PaaS でも**利用者が自分で**やる（アプリは自分で持ち込んだもの）。全部任せられるのは SaaS だけ
( 同じ節に出る言葉
+ 責任共有モデル — セキュリティの責任を提供者と利用者で**分担**
+ SOA — 機能を「サービス」の部品にして組み合わせる。ESB＝サービス同士をつなぐ基盤
+ マイクロサービス — もっと小さい独立したサービスの集まりで作る
)
@end

@card 半導体の分業 | 06-1#分業のかたち
| 名前 | 企画・設計 | 製造 | 販売 |
| 垂直統合型（IDM） | ○ | ○ | ○ |
| ファブレス | ○ | × | ○ |
| ファウンドリ | × | ○ | × |
| デザインハウス | ○ | × | × |
(
- 垂直統合型デバイスメーカー（IDM） — **全部自社**（Integrated Device Manufacturer）。例：Intel・Samsung
+ ファブレス — **工場なし**。設計して売る（Fabless）。例：Apple・NVIDIA
+ ファウンドリ — **製造だけ**請け負う（Foundry）。例：TSMC
+ デザインハウス — **設計だけ**請け負う（Design House）
)
> **Fab＝工場**（fabrication）。ファブ**レス**＝工場**なし** → 設計＋販売。ファウンドリ＝**鋳造所**（工場）→ 製造だけ。**Apple（ファブレス）が設計して TSMC（ファウンドリ）が作る**＝**水平分業**
( 分業と統合の言葉
+ 水平分業 — 設計と製造を**別の会社**で分ける（Apple＋TSMC）
+ 垂直統合（M&Aの意味） — 上流・下流の会社を**買って1社でやる**（製鉄会社が鉱山会社を）。同業種を買うなら**水平統合**
)
! 「フランチャイザー」は半導体と無関係（コンビニ本部のように、商標と販売権を貸す側）
@end

@card パーミッションマーケティングと仲間 | 06-1#売り方
| 手法 | 一言で | 例 |
| パーミッション | 客の**同意（許可）をもらってから**売り込む。同意の範囲を**少しずつ広げる** | メルマガ登録・LINE友だち追加・無料サンプル |
| アフィリエイト | **成約したら報酬**を払って、他人のサイトで紹介してもらう | ブログの Amazon リンク |
| バイラル | **口コミで勝手に広まる**仕組みを作る（viral＝ウイルスのように） | SNSでバズる・シェアキャンペーン |
| 差別型 | **客層（セグメント）ごとに**売り方を変える（無差別型＝全部に同じ、集中型＝1つの層に絞る） | 若者向けと高齢者向けで別の広告 |
パーミッションの流れ（LINE公式で）：①友だち追加で**クーポン**（きっかけ）→ ②追加した人に**少しずつ**情報を送る → ③「誕生日も教えて」と**同意の範囲を広げる** → ④**常連客**になってもらう
( 見分け方（Permission＝許可。許可をもらってから売る）
+ パーミッション — 「**同意**」「**許可**」
+ アフィリエイト — 「**成功報酬**」
+ バイラル — 「**口コミ**」「**自然に広がる**」
+ 差別型 — 「**セグメントごとに違う**」
)
@end

@card アグリゲーションサービスと仲間 | 06-1#売り方
**アグリゲーションサービス**（Aggregation：集約）＝**バラバラのサービスを1か所にまとめて**、一括で見たり比べたりできるようにするサービス
例：**マネーフォワード**（複数の銀行・カード・証券口座を**1つのアプリでまとめて見る**）、**価格.com・トリバゴ**（いろんなお店・ホテルの値段を**まとめて比較**）
| 名前 | 一言で | 例 |
+| アグリゲーションサービス | 複数のサービスを**まとめて一括表示** | マネーフォワード |
| フランチャイズ | 本部にお金を払って**看板・ノウハウを借りる** | コンビニ |
| オムニチャネル | **1つの会社**の店舗・EC・アプリを**つなげる** | ネットで注文して店で受け取り |
| エスクローサービス | **第三者がお金を一時預かり**して安全に取引 | メルカリの支払い |
( オムニチャネルとの見分け方（ここが引っかけ）
+ オムニチャネル — **1社**が自分の**窓口同士**をつなぐ（無印良品のアプリ・店・EC が連動）
+ アグリゲーション — **複数の会社**のサービスを**外から束ねる**
)
> 覚え方：**Aggregate＝集める**。「**分散してるものを一括で**」と書いてあればアグリゲーション
( 同じ節に出る言葉（売る場所・ネットの稼ぎ方）
+ ボランタリーチェーン — 独立した店同士が仕入れなどを共同化
+ O2O — ネットから実店舗へ誘導
+ ロングテール — ニッチ商品の合計が無視できない
+ フリーミアム — 基本無料・高機能は有料
)
@end

@card デジタルツインとスマート〇〇（IoT） | 06-1#IoT
**デジタルツイン**＝現実の物を**ネット上にそっくり再現**して、シミュレーションや予測をする。**ゲームの中に、現実の街の双子（ツイン）を作る**感じ
1. **センサー（IoT）**で現実のデータを集める
2. 仮想空間に**リアルタイムで再現**
3. そこで「もし〜したら？」を**シミュレーション**して、結果を現実に活かす
( よく一緒に出る4つ
+ スマートグリッド — **電力網**を IT で賢くして、需要と供給を**自動で調整**。例：電気が余ったら家の蓄電池にためる
+ スマートメーター — 電気の使用量を**自動で電力会社に報告**するメーター。例：検針員が家に来なくていい
+ デジタルツイン — 現実の物を**ネット上にそっくり再現**して、シミュレーション・予測。例：工場を PC 上に再現して「機械が壊れる時期」を予測
+ サーバ仮想化 — 1台の物理サーバで**複数のサーバ OS**を動かす（IoT とは別の話）。例：VMware・Xen
)
( 関連してよく出る
+ CPS（サイバーフィジカルシステム） — 現実（フィジカル）とネット（サイバー）を**つないで**、データで現実を良くする仕組み全体。デジタルツインはその代表例
+ スマートシティ — 街全体を IoT・AI で**効率化**（交通・エネルギーなど）
+ エッジコンピューティング — データを**現場の近く**で処理して、遅延と通信量を減らす
+ HEMS（Home Energy Management System） — **家の中**の電気を見える化・管理
+ IoTの4段階 — 監視 → 制御 → 最適化 → 自律化（人を介さず機械同士で判断して動く）
)
( 見分け方
+ デジタルツイン — 「**現実世界を仮想空間に再現**」「**シミュレーション・予測**」
+ スマートグリッド — 「**電力網**」「**需給調整**」
+ スマートメーター — 「**電力使用量を自動報告**」
)
@end

@card IoTの電気（エネルギーハーベスティング…） | 06-1#IoT
**エネルギーハーベスティング**（Energy Harvesting：環境発電）＝周りにある**振動・熱・光・電波**などの小さなエネルギーを**集めて電気にする**技術
( IoTの電力系4つ
+ エネルギーハーベスティング — 周りのエネルギーで**発電する**。例：歩く振動で光る床、体温で動く腕時計
+ ノーマリーオフコンピューティング — **必要なときだけ電源 ON** で節電。例：普段は寝てて、センサーが反応したら起きる（不揮発メモリで状態を残す）
+ EMS（Energy Management System） — 電気の**使用量を見える化・最適化**。例：工場やビルの電力管理システム（家なら HEMS、ビルなら BEMS）
+ PoE（Power over Ethernet） — **LAN ケーブルで電気も送る**。例：天井の防犯カメラ・Wi-Fi アクセスポイント
)
( 見分け方（動詞で判定）
+ エネルギーハーベスティング — 「**作る**」（発電・収穫）
+ ノーマリーオフ — 「**止める**」（必要なときだけ ON）
+ EMS — 「**管理する**」（把握・最適化）
+ PoE — 「**送る**」（LAN ケーブル）
)
> 覚え方：**Harvest＝収穫**。畑で作物を集めるみたいに、周りのエネルギーを**集める**
( 同じ節に出る言葉（電気と IoT）
+ スマートメーター — 電気の使用量を**自動で電力会社に報告**
+ スマートグリッド — **電力網**を IT で賢くして、需要と供給を**自動で調整**
)
@end

## 企業活動・法務
@card 投資するか決める指標 | 06-2#投資するか決める指標
4つとも**投資するべきか判断する指標**。例：100万円投資して、毎年30万円もうかる
| 指標 | 何を見る？ | 例での答え |
| ROI | 投資に対して**何%**もうかるか（Return On Investment） | 30万 ÷ 100万 ＝ **30%** |
| PBP | **何年で**元が取れるか（Pay Back Period） | 100万 ÷ 30万 ≒ **3.3年** |
| NPV | 将来のもうけを**今の価値**に直して、投資額より大きいか（Net Present Value） | **0より大きければGO** |
| IRR | NPVが**ちょうど0**になる利回り（Internal Rate of Return） | **期待する利回りより大きければGO** |
> **現在価値**とは：来年の100万円は、今の100万円より価値が低い（今もらえば利息がつくから）。だから将来のお金は**割り引いて**比べる。NPV と IRR はこの考え方を使う
( 式
- ROI — 利益 ÷ 投資額
- PBP — 投資額 ÷ 毎年のもうけ。お金の**時間価値を考えない**のが弱点
+ NPV — Σ 将来のお金 ÷ (1＋割引率)^年 − 投資額
+ IRR — NPV がちょうど0になる割引率
)
> 現在価値の例：割引率10%なら、来年の110万円＝今の100万円
( 見分け方（日本語名もセットで）
- PBP（回収期間） — 「**期間**」「**何年で回収**」
- ROI（投資利益率） — 「**利益 ÷ 投資額**」「**割合**」
+ NPV（正味現在価値） — 「**現在価値**」「**0を上回るか**」
+ IRR（内部収益率） — 「**割引率**」「**内部収益率**」
)
! ROI は**割合**（%）、PBP は**年数**。「何年で元が取れるか」を ROI と取り違えない
@end

@card 知的財産権 | 06-3#知的財産権
**4つだけじゃない**。全体はこう
(
+ 産業財産権（特許庁に登録が必要） — 特許権・実用新案権・意匠権・商標権
- 著作権 — **登録不要**。作った瞬間に発生
- その他 — **営業秘密**（不正競争防止法）・**回路配置利用権**（半導体の回路設計）・**育成者権**（植物の新品種）
)
| 名前 | 守るもの | 期間 |
| 特許権 | **発明**（高度な技術アイデア） | 出願から**20年** |
| 実用新案権 | **ちょっとした工夫**（形・構造） | 出願から**10年** |
| 意匠権 | **デザイン**（見た目） | 出願から**25年** |
| 商標権 | **ロゴ・名前** | 登録から**10年**（**更新すれば永遠**） |
| 著作権 | **表現**（文章・音楽・プログラム） | 作者の**死後70年**（法人は公表後70年） |
| 営業秘密 | **社外秘の情報**（顧客名簿・製法など） | 秘密である限り |
( よく出るポイント
- 登録 — **著作権は登録不要**。他は基本的に**登録が必要**
- プログラム — 著作権で**守られる**。でも**アルゴリズム・プログラム言語・規約**は**守られない**（表現じゃなくて考え方だから）
+ 営業秘密の3条件 — **秘密管理性**（ちゃんと秘密として管理）・**有用性**（役に立つ）・**非公知性**（世間に知られてない）
)
( 著作権は誰のもの？何がOK？
- 守られる — 設計書・ソースコード・目的プログラム・マニュアル
- 職務著作 — 社員が仕事で作った → **会社**のもの
+ 派遣で作った — **派遣先**のもの
+ 開発を委託（請負）した — 特に決めてなければ**受託した側**のもの
+ やってOK — バックアップ用の複製、自社で使うための改変
+ やっちゃダメ — 子会社などに複製して配る、海賊版と**知ってて手に入れて**使う
+ 著作者人格権 — 公表権・氏名表示権・同一性保持権。**譲渡できない**
+ クリエイティブ・コモンズ — 表示・非営利・改変禁止・継承などの条件を付けて利用を許可
)
( 見分け方（定義文のキーワード）
- 特許 — 「**自然法則**」「**技術的思想**」「**高度**」
- 実用新案 — 「**物品の形状・構造**」（高度じゃない）
- 意匠 — 「**美感**」「**視覚**」
- 商標 — 「**標章**」「**商品や役務**」
- 著作権 — 「**思想・感情の表現**」
)
@end

@card RFI・RFP・RFC（調達の流れ） | 06-3#働かせ方と頼み方
**調達の流れの順番**で並べると一発で覚えられる：**RFIで情報集め → RFPで提案をもらう → 契約 → RFCで変更**
| 順番 | 何をする？ | リフォームで |
| ① RFI | 業者に「**どんな技術・実績ある？**」と**情報をもらう** | 何社かに「**どんなことできます？**」と聞く |
+| ② RFP | 条件を示して「**提案書と見積もりを出して**」と頼む | 「予算100万でキッチン直したい。**プラン出して**」 |
| ③ 契約締結 | 役割分担を確認して**契約**を結ぶ | 「**この業者に決めた**」 |
| ④ RFC | 契約後に「**ここ変えて**」と依頼する | 「やっぱり**壁紙の色を変えて**」 |
( 正式名（最後の1文字だけ見る）
- RFI — Request for **I**nformation（**情報提供**依頼書）＝まず**情報**集め
+ RFP — Request for **P**roposal（**提案**依頼書）＝次に**提案**をもらう
- RFC — Request for **C**hange（**変更**依頼書）＝契約後の**変更**。サービスマネジメントの変更管理の RFC（変更要求）と同じ言葉 {{05-2}}
+ RFQ — Request for **Q**uotation（**見積**依頼書）。値段だけを聞く
)
( 見分け方（問題文の言葉 → 答え）
- RFI — 「**情報の提供を依頼**」（利用できる**技術・製品**、ベンダの**導入実績**など）
+ RFP — 「**提案書の提出を依頼**」（対象システムや**調達条件**を示す）
- RFC — 「**契約後の変更**」（取り決めた内容の**変更を要請**）
- 契約締結の依頼 — 「役割分担などを確認し、**契約の締結を要請**」
)
> おまけ：RFP で集まった提案から業者を選ぶときの**提案の評価基準は、提案が集まる前に決めておく**のが基本（公平に選ぶため）
! ネットワークの話で出る **RFC** は Request for **Comments**（インターネットの技術仕様を書いた文書。IETF が出す）。調達の RFC（変更依頼書）とは別物
( 同じ節に出る言葉（調達）
- グリーン調達 — 環境にやさしい物を優先して買う。CSR調達＝調達先にも社会的責任を求める
+ 請書 — 注文書に対して「引き受けます」と返す書類
)
@end

@card トレーサビリティ（さかのぼれること） | 06-3#共通のルール
**トレーサビリティ**（Traceability：追跡可能性）＝「**なぜ今こうなってるのか**」を、過去の記録をたどって**さかのぼれる**こと
( 例
- 食品 — スーパーの牛肉の番号から、**どの農家のどの牛か**までたどれる
+ システム開発 — 「この機能は**どの要件から生まれて、誰がいつ・なぜ変更したか**」をたどれる
)
@flow 要件定義 > 設計 > プログラム > テスト || 矢印でつながっていて、**どっち向きにも**たどれる状態
( 開発でのイメージ
+ 要件から — 「この要件は**どのコードとテスト**で実現してる？」
+ コードから — 「このコードは**どの要件**のため？」
+ だから — 要件が変わったとき、**どこを直せばいいか**がすぐわかる
)
> Gitで：コミット履歴に「**何を・なぜ変えたか**」がちゃんと残っていて、`git log` で**過去の判断までさかのぼれる**状態
> 覚え方：**Trace（たどる）＋ability（できること）**＝**たどれること**
( 見分け方（問題文の言葉 → 答え）
+ トレーサビリティ — 「**過去の履歴・意思決定を記録**」「**追跡できる**」「**さかのぼって参照**」
+ 要件定義の問題での形 — 「利害関係者の**要求の根拠と成果物の相互関係**が文書化」「仕様変更を、求められる**品質に立ち返って検証**できる」
)
! 「仕様を固めて**以降は変更できない**」はトレーサビリティではない。変更が起きても、**元の要求までさかのぼって確かめられる**ことがトレーサビリティ
( 同じ節に出る言葉（共通フレーム）
+ 企画プロセス — システム化構想（経営課題・事業環境の分析）→システム化計画
+ 要件定義プロセス — 利害関係者を識別→要件を引き出す（要件の識別）→評価→合意
+ 要件の種類 — 業務要件→機能要件→非機能要件（性能・可用性・セキュリティ）
)
@end
