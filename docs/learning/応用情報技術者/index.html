フラッシュメモリ（SSD・USBメモリ）は同じ場所に何回も書くと壊れる → 書き込む場所を全体に散らして平均的にすり減らすのがウェアレベリング。消しゴムの同じ角ばかり使うとすぐダメになる、全部の角を順番に使えば長持ち

ウェアレベリング書込みを均等に分散 → 寿命を延ばすライトアンプリフィケーション頼んだ量より余計に書き込んでしまう現象（書込み増幅）→ 寿命を縮める（悪い方）デフラグHDDでバラバラのデータを並べ直して速くする → 寿命とは関係なし（SSDには不要）ジャーナリングファイルの変更をログに記録して、障害時に復旧しやすくする → 寿命とは関係なし

仮想記憶（ページング〜LRU）→02-3

全部「メモリ管理」の話で、1つの流れでつながっている。勉強机で例える：主記憶（メモリ）＝勉強机（狭いけどすぐ使える）、ディスク＝本棚（広いけど取りに行くのが遅い）、プログラム＝教科書

  1. 仮想記憶：机が狭くても、本棚も机の一部みたいに使う。必要なページだけ机に出す
  2. ページング／セグメンテーション：机への置き方を決める
  3. ページテーブル：どこに置いたかの台帳で場所を管理
  4. ページフォールト：使いたいページが机にない（本棚にある）
  5. ページ置換え（LRU など）：机が満杯なら、何を片付けるか決める
  6. フラグメンテーション：置き方次第で、空きがバラバラになる
  7. ガーベジコレクション：使い終わったメモリを自動で回収（ページの話とは別）
置き方区切り方弱点
ページング同じサイズ（固定長）。全部同じ大きさのファイルに分けて置く最後のファイルが余る（内部断片化）
セグメンテーション意味のまとまり（可変長）。「数学」「英語」とバラバラの大きさで置く隙間ができる（外部断片化）
台帳と「机にない！」
ページテーブル「このページは机のどこ？本棚？」を記録した台帳。MMU がこれで仮想アドレス → 実アドレスに変換多段ページテーブル台帳を必要な分だけ作る → 全ページ分の台帳は要らないTLBアドレス変換の結果を覚えておく専用キャッシュ（毎回台帳を見に行かない）ページフォールト使いたいページが主記憶にない状態（割込みが起きる）フォールト時の順番フォールト → 片付けるページを決める → 片付けて（ページアウト）→ 本棚から持ってくる（ページイン）デマンドページングフォールトしてから読む。プリページング＝先読み
置換え片付けるページ
FIFO一番最初に置いたもの
LRU一番長く使ってないもの（Least Recently Used）
LFU使った回数が一番少ないもの（Least Frequently Used）
LRU・FIFO の置換え回数は、表を描いて1つずつ埋める。頭の中だけだとほぼ間違える
断片化と回収
フラグメンテーション（断片化）空きはあるのに、バラバラで使えない状態。セグメンテーションで起きやすい（大きさがバラバラだから）コンパクション使ってる物を端に寄せて空きをまとめる（断片化の対策）ガーベジコレクション（GC）プログラムが使い終わったメモリを自動で回収する機能（Java・JavaScript など）。机に散らかったゴミを自動で捨てる係スラッシングメモリ不足でページ置換えが多発して激遅（CPU 使用率↓・ディスク I/O↑）
計算
ページテーブルの大きさ2^(L−N) × 2^E（仮想空間 2^L・ページ 2^N・1項目 2^E バイト）平均アクセス時間主記憶時間 ＋ フォールト処理時間 × フォールト率（単位をそろえる）
つながりを1行で：仮想記憶で机を広く見せる → ページング／セグメンテーションで置き方を決める → ページテーブルで場所を管理 → 机にないとページフォールト → LRU などで片付ける物を決める → 置き方次第で断片化 → 不要なメモリは GC が回収
ページングでは外部断片化は起きない（固定長だから）。GC はページフォールトと無関係（プログラムのメモリの後片付け）

3DCGの技法→02-4

3DCG の技法はキーワード1語で見分けられる。役割で5つに分けて覚える

① 光・影をつける
レイトレーシング目（視点）から光の経路を逆にたどって、反射・屈折・透過を計算。「視線追跡」「反射・屈折」「鏡面」ラジオシティ法面と面の間で光が何度も跳ね返るのを計算（やわらかい間接光）。「拡散反射面の相互反射」レイキャスティング視線を飛ばすだけ。反射・透過は追わない（簡易版）シェーディング光の当たり方で陰影をつける。「陰影」「明るさ」
② 見えない面を消す（陰面消去）
Zバッファ法画素ごとに一番手前の物だけ描く。「奥行き（Z値）」「画素ごとに奥行きの最小値を保持」
③ 表面の見た目をつける
テクスチャマッピング表面に画像（模様）を貼る。「模様を張り付ける」「壁紙」バンプマッピング表面に凹凸があるように見せる。「凹凸」
④ 形を作る（モデリング）
ポリゴン小さな多角形の組合せで形を作る。「多角形」メタボール球の集まりで、なめらかな形を作る。「球・楕円体」「滑らか」ワイヤーフレーム線だけで形を表す。「線」「骨組み」
⑤ 仕上げ
アンチエイリアシング斜め線のギザギザをなめらかにする。「ギザギザ」「ジャギー」レンダリング全部まとめて画像として描く（最後の工程）。「描画」「画像に変換」ボリュームレンダリング空間中のデータ（CT・MRI など）から明るさを計算して描く。反射・透過は追わない
覚え方：レイ＝光線。トレーシング（追う）なら反射まで、キャスティング（投げる）なら投げるだけ。ラジオシティ＝光の跳ね返り合い
見分け方（よく出る説明文）
テクスチャマッピング「物体の表面に、別に定義された模様を張り付ける」レイトレーシング法「視線と物体の交点のうち視点に最も近い交点を選ぶ」（視線をたどって隠面消去する使い方）Zバッファ法「画素ごとに奥行き（距離）の最小値を保持」ラジオシティ法「拡散反射面間の相互反射を考慮」ボリュームレンダリング「反射・透過方向の追跡を行わず、空間中のデータから輝度を計算」（視線を投げるだけ＝レイキャスティングで描く）
選択肢は説明と名前がシャッフルされる（「レイトレーシング法は模様を張り付ける」など）。名前ではなく説明文のキーワードから技法を決めて、名前と合っているかを見る

OP25Bとサブミッションポート→03-6

セットで出るから、流れで押さえる

OP25B（Outbound Port 25 Blocking）＝スパム対策で、25番ポートで外に直接メールを送るのを禁止する／サブミッションポート（587番）＝その代わりの正規ルート。ID・パスワードで認証（SMTP-AUTH）してから送らせる

  2. 対策として、ISP が 25番ポートの外向き通信をブロック（OP25B）
  3. でもそれだと、普通の人も外からメールを送れなくなる
  4. そこで 587番（サブミッションポート）を用意して、認証した人だけ送れるようにする

モジュール結合度と強度→04-1

結合度（Coupling）＝モジュール同士のつながり → 弱いほど良い。強度（Cohesion・凝集度）＝モジュール内部のまとまり → 強いほど良い。合言葉は「疎結合・高凝集」（外とはゆるく、中はしっかり）

結合度（良い順）何を共有・受け渡しする？
① データ結合引数で単一のデータ（Data Coupling）
② スタンプ結合引数で構造体（レコード）（Stamp）
③ 制御結合引数で動作を指示（フラグなど）（Control）
④ 外部結合グローバル変数（単一）（External）
⑤ 共通結合グローバルな構造体（Common）
⑥ 内容結合相手の内部を直接いじる（Content）
語呂「です、背が今日ない」＝データ→スタンプ→セイギョ→ガイブ→キョウツウ→ナイヨウ。3グループで見る：引数で渡す（①〜③）／グローバルで共有（④⑤）／中身を直接いじる（⑥）。「単一 → 構造体」の順に悪くなるパターンが2回出てくる
強度（良い順）まとめた理由
① 機能的強度1つの機能だけ（Functional）
② 情報的強度同じデータを扱う機能を集めた（入口は別々）（Informational）
③ 連絡的強度同じデータを使って順番に処理（Communicational）
④ 手順的強度決まった手順の順に並べた（Procedural）
⑤ 時間的強度同じタイミングで動く（例：初期化処理）（Temporal）
⑥ 論理的強度似た処理をまとめて、フラグで切り替え（Logical）
⑦ 暗合的強度たまたま寄せ集めただけ（Coincidental）
語呂「気丈に連れて、持論案」＝キノウ→ジョウホウ→レンラク→テジュン→ジカン→ロンリ→アンゴウ。まとめた理由がちゃんとしてるほど強い：1機能 → 同じデータ → 手順 → 時間 → 似てるだけ → 偶然
見分け方（問題文の言葉）
データ・スタンプ・制御「引数」→ 中身が単一か、構造体か、指示か外部・共通「大域・グローバル」→ 単一なら外部、構造体なら共通内容「内部を直接参照」「JUMP」
「引数」だけ見てデータ結合系と決めない。引数で動作を指示していたら制御結合

現在価値とは：来年の100万円は、今の100万円より価値が低い（今もらえば利息がつくから）。だから将来のお金は割り引いて比べる。NPV と IRR はこの考え方を使う

順番何をする？リフォームで
① RFI業者に「どんな技術・実績ある？」と情報をもらう何社かに「どんなことできます？」と聞く
② RFP条件を示して「提案書と見積もりを出して」と頼む「予算100万でキッチン直したい。プラン出して」
③ 契約締結役割分担を確認して契約を結ぶ「この業者に決めた」
④ RFC契約後に「ここ変えて」と依頼する「やっぱり壁紙の色を変えて」
正式名（最後の1文字だけ見る）

要件から「この要件はどのコードとテストで実現してる？」コードから「このコードはどの要件のため？」だから要件が変わったとき、どこを直せばいいかがすぐわかる
Gitで：コミット履歴に「何を・なぜ変えたか」がちゃんと残っていて、git log で過去の判断までさかのぼれる状態
覚え方：Trace（たどる）＋ability（できること）＝たどれること
見分け方（問題文の言葉 → 答え）
トレーサビリティ「過去の履歴・意思決定を記録」「追跡できる」「さかのぼって参照」要件定義の問題での形「利害関係者の要求の根拠と成果物の相互関係が文書化」「仕様変更を、求められる品質に立ち返って検証できる」
「仕様を固めて以降は変更できない」はトレーサビリティではない。変更が起きても、元の要求までさかのぼって確かめられることがトレーサビリティ
